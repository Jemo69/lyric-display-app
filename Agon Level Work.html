Four problems that need a bigger model

These are not bugs. Each one is a design problem where the failure mode is emergent — it only appears under reconnect, under a second writer, under a throttled window, or at the boundary between two translations — and where every naive fix breaks something else that is already load-bearing during a live service. Hand these to a large model with a wide context window. A small model will patch the symptom and leave the system less correct than it found it.

4 selected Selection rule: fix requires a protocol, a data model, or a scheduling policy — not a patch All line numbers verified against working tree Read-only survey · no code changed

Problem 01 · Replication protocolDepth 4/4Emergent: reconnect + 2 writers
01

Reconnect split-brain: full-state push in both directions, merged last-writer-wins, no revision or epoch anywhere in the system.

The claimOn every reconnect the desktop client pushes its entire local state at the server while the server pushes its entire state back at the client. Neither carries a version. The deterministic wire order is: receive the good server values → overwrite them with your own stale values → the server re-affirms your stale values and broadcasts them to every window. Losing a style edit is the mild outcome; the severe outcome is a custom output registered by a mobile controller getting pruned, its mode templates deleted, and its background media removed from disk.

The mechanism

Three actors write the same session on every reconnect, in a fixed but wrong order.

1 · The client pushes local state synchronously on connect, before any snapshot arrives.

// src/hooks/useSocketEvents.js:744-790   (desktop re-pushes all content 1s later)
setTimeout(() => {                                                     // :745

  socket.emit('lineUpdate', { index: ... });
  socket.emit('showStateUpdate', ...);

2 · The server merges with a spread — pure last-writer-wins — then echoes to everyone, including the pusher.

Why a bigger model

  • You cannot just make "server wins". The migration path at useSocketEvents.js:101-103 is intentional first-run behaviour: a cold desktop must be able to bootstrap an empty server. "Server wins" unconditionally breaks first launch; "client wins" unconditionally is what caused this bug. The solution needs an explicit empty-or-epoch comparison on both sides.
  • Ordering is only nominally safe. ready flips on receipt of currentState (src/context/ControlSocketProvider.jsx:215-220), which triggers the offline-queue flush (:331-340) after the snapshot — replaying pre-disconnect deltas over freshly-fetched authoritative state. Fixing the push without fixing the queue leaves the same race.
  • Deletion needs tombstones. Whole-registry replace with derived deletedIds must become per-output upsert-or-tombstone, or a stale snapshot keeps deleting media. That is a schema change with a migration for persisted sessions.
  • Two snapshot channels apply different subsets with different coercions. currentState (:57-167) coerces freenote → song and skips empty lyrics/title; periodicStateSync (:576-660) honours freenote and applies timestamps unconditionally. Same canonical state, different client mode depending on which channel delivered it. Any redesign has to unify two reducers that were written against each other.
  • Nothing tests convergence. serverEventsDisconnect.test.js, outputPresence.test.js, outputTemplateSync.test.js all cover happy paths. There is no test anywhere that asserts two clients converge after one reconnects with divergent state — so the new protocol must define its own oracle before it can be verified.

What any solution must preserve

  • Late-joining outputs still render correct slide + styles within ~1s (the 100ms auto-snapshot at events.js:1877-1882 is load-bearing for cold starts).
  • Cold-start bootstrap: desktop can initialise an empty server from local state.
  • Server disk-restore vs desktop localStorage-restart resolve deterministically, with a persisted epoch on both sides (sessionPersistence.js already carries an unused savedAt/version).
  • Registry updates never delete media or prune templates on the basis of a stale snapshot.
  • Legacy consumers keep receiving both outputToggle and showStateUpdate (shared/showControl.js:71-89), and permission-filtered fan-out stays intact (chords/stage fields to stage only, events.js:1951-1958).
  • Manual "Sync Outputs" (src/hooks/useSyncOutputs.js:24-95) and the REST/API writers in server/events.js keep working against whatever new write path is introduced.

Problem 02 · Bible alignmentDepth 4/4Emergent: 2nd translation
02

No canonical book identity: a book number means something different in every translation, and every cross-translation consumer assumes it does not.

The claimEach parser invents its own 1–66 numbering scheme. OSIS books are numbered positionally from the file, so a Catholic or Orthodox file with deuterocanonical books shifts every number after Tobit — integer equality across translations is not merely inconvenient, it is wrong. Downstream, the parallel display reuses the primary translation's integer for the secondary, search applies one English query to every translation, and a numeric reference from translation A is re-resolved in translation B with a stale closure.

Why a bigger model

  • The number is the API. reference.book is a bare integer in persisted history, in setlist files on disk, in socket payloads, and in HTTP/mobile consumers. You must introduce a canonical layer (OSIS codes + per-format and per-language alias tables) behind an integer that keeps its exact shape — and decide, per format, how to map into it for already-imported translations that recorded no source format.
  • Deuterocanon breaks naive mapping. Positional OSIS numbering means integer equality across translations is a correctness bug, not a naming inconvenience. A Catholic OSIS file and a KJV disagree about book 30 onward, which silently poisons buildOffsetId as well.
  • Joint pagination is an optimization, not a loop. Given primary text P and secondary text S — different lengths, different verse sets after versification, possibly different split methods — produce k slide pairs minimizing column imbalance, semantic misalignment, and overflow of the shared geometry budget (bibleSplitter.js:699-730), while never cutting words or wj markup, and staying stable as the operator steps slides. It cannot be solved per-slice, because the socket only ships pre-split slide arrays (sanitizeParallelPayload) — the receiver has no verse-level structure to realign with, so the payload contract must grow without breaking older readers.
  • Hard parity contracts already exist in tests. bibleSplitterTagSafe.test.js:80-89 requires the tag-safe method to equal the punctuation method for plain text at every maxChars/tolerance; reversibility (normalize(slides.join(' ')) === normalize(text)) is asserted throughout; bracket invariants in bibleSplitterBrackets.test.js:88-101. Any change to splitting must hold all of them.
  • Zero real fixtures. BibleImportButton.test.jsx:11-13 mocks shared/bible entirely. There is not one test that parses a real Bible file, and the repo contains no .xml/.json Bible fixtures. The risky cases — OSIS names, non-English books, mixed-format numbering, deuterocanon — are structurally untested, so the solver must build the oracle before building the fix.

What any solution must preserve — including the standing product constraint

  • AGENTS.md: the Import Bible Translation button stays. It must remain visible in User Preferences > Bible, keep the shared src/components/Bible/BibleImportButton.jsx wired into both UserPreferencesModal.jsx and BibleControlPanel.jsx, keep accepting .xml and .json, keep persisting through BibleStore, keep selecting the imported translation, and keep success/failure feedback. BibleImportButton.test.jsx and tests/UserPreferencesModal.test.jsx must stay green. Do not hide it behind a flag, do not replace it with an import tab. Import may record new metadata (format, canonical ids) — it may not change shape.
  • reference.book numeric shape and the searchBible result object unchanged (crossChapterReference.test.js:158-199 pins it).
  • parseBible/parseBibleFromFile signatures stay usable from main/ipc.js:1310,1321 and server/bibleManager.js:177.
  • The secondary payload subset { bible, text, fullText, slides } keeps working for older readers (server/events.js:93-96); sanitizeParallelPayload never throws.
  • Single-translation render path stays byte-identical (bibleParallel.js:56-57 comment says so explicitly); bibleParallel.test.js and bibleParallelPairing.test.js keep passing, including offset persistence.
  • bibleSplitter.js:772-775: pure string/regex tokenizing, no browser DOM APIs, no new dependencies.

Problem 03 · DurabilityDepth 4/4Emergent: shutdown + ENOSPC + orphan
03

The session snapshot serializes the entire world on every keystroke, dies silently on a full disk, and is fenced by nothing while three processes write.

The claimThirty-two call sites mark the whole session dirty; a 250 ms debounce then re-stringifies a payload that can reach ~100 MB (the setlist alone is 50 files × 2 MB). Write failures are swallowed by a console.warn and the IPC channel that reports capacity failure has no handler at the other end. Shutdown is fire-and-forget behind a 300 ms process.exit and a 2 s SIGKILL escalation. Meanwhile the snapshot's producer and consumer have drifted: one writes a field nobody populates, and reads one nobody writes.

The mechanism

1 · Every mutation dirties the world; every debounce serializes the world.

// server/events.js:134-142  + 32 call sites of notifySessionStateChanged()
//   styleUpdate, lineUpdate, tickerAdd, scheduleControl, registry update, template apply…

// server/sessionPersistence.js:164-193
async function writeSnapshot() {
  if (saveInFlight) { saveQueued = true; return; }
  saveInFlight = (async () => {
    const snapshot = createSessionSnapshot();                 // full state, sync JSON.stringify
    await fs.mkdir(path.dirname(sessionFilePath), { recursive: true });
    const tmpPath = `${sessionFilePath}.${process.pid}.tmp`;  // pid-only, no lease/lock
    try {
      await fs.writeFile(tmpPath, JSON.stringify(snapshot), 'utf8');
      await fs.rename(tmpPath, sessionFilePath);              // no directory fsync
    } finally {
      await fs.rm(tmpPath, { force: true }).catch(() => {});
    }
  })();
}
Payload scaleevents.js:336 MAX_SETLIST_FILE_CONTENT_BYTES = 2 * 1024 * 1024 · events.js:334 totalAfterAdd > 50 throws → up to ~100 MB re-stringified synchronously, up to 4× per second, on the same event loop that serves socket.io heartbeats and the 1s schedule tick (events.js:924-927).
Same payload also broadcast per socketevents.js:113-132 and buildCurrentState at :1938 ship the full setlist to every client type. Inbound is capped at 5 MB (server/index.js:699); outbound is not.

2 · Failure is reported to a parent that never listens.

6 · An orphaned server blocks the next launch entirely.

Why a bigger model

  • It is a storage-engine design problem. The options are incremental/dirty-field persistence or an append-only journal with snapshot compaction — each with a different answer to: how do you keep bulk content (setlist, raw lyrics) out of the hot write path without breaking restorability, and how do you keep the on-disk format version: 2 with migrateSessionSnapshot (sessionPersistence.js:103-126) able to read everything already on users' disks?
  • Writer fencing across processes, with no new infra. Electron main + its forked server + a potential orphan all touch the same file and the same keychain. The temp-file name carries only a pid. A correct design needs a lease or lock that works offline, on Windows and POSIX, without adding a database or a daemon — and it must break ties in favour of the writer that is actually alive.
  • Backpressure that does not stall the show. The write must not block the event loop (heartbeats, the 1s schedule tick, socket fan-out), must coalesce under a sustained edit storm, and must surface ENOSPC to the UI. shared/storageErrors.js:25-44 already provides isStorageCapacityError/toStorageWriteFailure and is used by sessionPersistence's sibling paths — but never wired to the user.
  • Shutdown must become a bounded, awaited operation. Today three timers with three deadlines (300 ms exit, 2 s SIGKILL, immediate SIGKILL on Windows) race one async flush. Making it correct means defining a maximum flush time, a degraded fast-path (journal tail only), and agreeing what "last change survived" means — while flushSessionStateNow() stays exported for SIGINT/SIGTERM.
  • Schema drift needs a contract test. Two dead fields prove producer and consumer evolved independently with nothing asserting they agree. The fix is not to delete the fields; it is to define the snapshot as a typed contract with a round-trip test, then migrate.

What any solution must preserve

  • Same file name and schema version (backend/realtime-session-state.json, version: 2) plus a working migration for existing files; LYRICDISPLAY_DATA_DIR awareness (index.js:88-90, sessionPersistence.js:147).
  • Fully offline and local: no database, no new infrastructure, no cloud.
  • Everything currently restorable stays restorable — lyrics, show state, ticker, outputs, templates, schedule, setlist ≤ 50 — and the two drifted fields must either become real or be removed with a migration.
  • flushSessionStateNow() keeps its export and its signal hooks; restore still happens before the first snapshot can be served.
  • Better-sqlite3 and keytar remain optional (graceful fallbacks exist at main/fileNavigator.js:311-314 and secretManager.js:223).

Problem 04 · Presentation clockDepth 4/4Emergent: N windows + hidden window
04

Eight animation mechanisms run on eight private clocks across independent renderer processes, with no shared epoch — and Chromium throttles them independently.

The claimThe server hands out line changes with no presentation timestamp. Every output applies it the moment it arrives and starts its animation on its own requestAnimationFrame timeline. Transition duration and easing are per-output settings, so the same wall-clock event renders as a cut on one projector, a 200 ms fade on another, and a 2 s spring on a third — each beginning at a different instant determined by socket latency. Worse, mode="wait" serializes exit before enter, so every line costs 2 × transitionSpeed of background-only time.

Why a bigger model

  • Every naive fix fails for a reason. Server-side "emit at T+Δ" adds network jitter to the start of the animation. Date.now() is not monotonic and is unsynced across processes. performance.timeOrigin differs per renderer. document.timeline.currentTime still needs a common epoch. Disabling backgroundThrottling makes hidden windows burn full CPU/GPU — the exact meltdown low-power mode exists to prevent — and does not help preview iframes or a browser tab.
  • It has to drive four incompatible mechanisms. React state, framer-motion's rAF, CSS keyframes, and the <video> media clock all need one monotonic presentation timeline that adds no measurable latency to a lyric change and survives a throttled window.
  • The transition state machine must be redesigned, not tuned. mode="wait" is what gives the deliberate "fade through background" look; replacing it with crossfade/exit-budget must bound worst-case latency and never yield more than one blank beat — while keeping the stage's direction logic (prevLineRef.current < current, StageOutput.jsx:1175,1191) correct.
  • Adaptive quality needs hysteresis or it pulses. Frame drops → quality down → frames OK → quality up → drops again is visible pulsing on a projector. And today there is zero telemetry: grep for fps|frameTime|PerformanceObserver|droppedFrame in src/ returns nothing. Canvas DPR, particle count and t0 are frozen at mount, so there is no path to degrade without a remount and no signal telling it when to.
  • Fixing the fan-out must come first. Any new cross-window telemetry channel makes the O(N²) outputMetrics echo worse. The order matters: de-amplify, then measure, then budget.

What any solution must preserve

  • A lyric change becomes visible within one frame of socket receipt — no added network delay, no "wait for a global tick" that could skip a line.
  • Never drop or reorder lineUpdate/lyricsLoad. The comment at server/events.js:1297-1299 is a hard requirement: "must land after lyricsLoad … to avoid a wrong-slide flash."
  • transitionSpeed 100–2000 ms and per-output animation choice keep working; Low Power Mode still yields an instantaneous cut (RegularOutput.jsx:425).
  • 60 fps on the lyric path under all quality tiers; only decorative layers may degrade (canvas DPR/particles, video preload, shadows/strokes, ticker).
  • outputMetrics keeps reporting adjustedFontSize/autosizerActive/viewport (the settings UI at OutputSettingsPanel.jsx:815-875 and serverEventsDisconnect.test.js:75-98 depend on it), and Bible slide splitting must not change when an output instance appears or disappears.
  • Hardware-acceleration changes are restart-bound (main.js:28-29) — a runtime budget cannot assume the GPU is available.
  • Metronome stays sample-accurate with FreeShow port semantics (preScheduleTime = 0.1, accent/secondary gain ratio, mid-play tempo change); countdown fires onExpire exactly once; autoplay never advances more than one line per interval.

Runner-ups · four more, not countedRanked

Real problems with real evidence, held back because the design surface is smaller than the four above. The first one is the highest-severity item in this survey — it is a runner-up on difficulty only.

R1 · Arbitrary-URL executor reaches the app's own localhost-only admin surface

main/ipc.js:544-550 — sanitize() only normalizes scheme and OCR artifacts (ø → 0); no host policy at all. The request runs in a main-process worker with Node fetch, which enforces no CORS and no localhost restriction, while server/index.js:163-184 protects GET /api/auth/join-code (exfils the controller join code) and POST /api/admin/secrets/rotate (rotates the JWT secret) with IP-based localhostOnly alone. Output automation fires automatically on every output toggle. Timeouts resolve but never abort: main/ipc.js:56-58 and src/utils/httpAction.js:44-56 both leave listeners and sockets open. Hard because localhost automation is the product (defaults localhost:5506, localhost:5505) — a naive block-private-ranges policy breaks it. Needs a destination policy allowing user-approved local automation while blocking the app's own admin surface and cloud metadata, plus one unified executor with AbortController propagation. Three divergent code paths today; no host or timeout test exists.

R2 · Two secret stores × two processes, with reads that write and normalization that mints new secrets

server/secretManager.js:107, 87 — plain writeFileSync to the destination (the repo's own hardened main/atomicFileSave.js is not used). loadSecrets() persists on every call — including from GET /api/health/ready at index.js:742, which main/backend.js:16 polls every second during startup. main/adminKey.js:17-74 reads the same keytar entry and the same file from a second process while the first may be mid-write → torn read → and _normalizeSecrets responds to a corrupt read by generating new JWT material and persisting it. Rotation is captured at module load (index.js:73-77) and returns "Server restart required." Failure mode is total: main/startup.js:19-38 hard-quits the app. Hard because keytar must stay optional, two processes must agree with no shared lock, and rotation must not invalidate live controllers mid-service.

R3 · File-navigator: any filesystem event triggers a full rescan and a synchronous whole-table rewrite on the Electron main thread

main/fileNavigator.js:576-582 — any event under any indexed root restarts a 450 ms timer → queueRebuild() → performRebuild() walks everything and, at :371-374, runs DELETE FROM navigator_files + re-INSERT for up to MAX_INDEX_FILES = 100_000 rows including up to 64 MB of file content — better-sqlite3 is synchronous, so every window and all IPC stall for the duration. The rebuild loop (:717-722) spins as long as events keep arriving (a log, media, or sync folder inside a root), and it re-installs all watchers each pass. Needs incremental per-file upsert, work off the main thread, a cost-based backpressure policy, and a migration story for the existing index file — while keeping the 60 s "no false completion" invariant the code comments at :707-708 guard. No test covers rebuild cost or watcher storms.

R4 · Compound multi-event transactions replayed through a lossy, unclassified queue

src/context/ControlSocketProvider.jsx:317-319 — on overflow the queue drops the oldest 50 entries regardless of event type and returns true, so useSyncOutputs.js:76-80 toasts "Outputs Synced successfully" for work never sent, while the parallel layer at src/hooks/useSocket.js:367-383 returns false for the same event names. A free-note load is five separate emits that depend on in-order delivery (LyricDisplayApp.jsx:416-439); dropping lyricsLoad while keeping the following lineUpdate applies an index into a different song's index space. No idempotency keys exist anywhere in server/events.js. Hard because it needs emission classification — coalescable state vs. monotonic deltas vs. atomic compound commands — plus a conflict-resolution policy for offline edits. Overlaps Problem 01 and should be solved with it, not before it.
