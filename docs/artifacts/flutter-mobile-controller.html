Flutter Mobile Controller

Plan · LyricDisplay · Mobile-first · Tablet-adaptive

Goal

Build a Flutter app that finds the LyricDisplay desktop app on the local network automatically, authenticates with the existing join-code flow, and acts as a full live controller: current song view, prev/next/goto, setlist management, output toggles, and Bible search.

The UI is designed phone-first, then adapts to tablets with a two-pane console layout. One codebase. Android ships first; iOS stays ready.

The desktop side already exposes everything we need — REST /api/v1/* plus Socket.IO broadcasts on port 4000, guarded by JWT join codes. The only server change required is a discovery beacon so phones can find it without typing an IP address.

Vocabulary & Direction Notes

  • "Lyrics display control" — driving what appears on the projected outputs from a second screen.
  • "Search local network" — the phone should discover the desktop app by itself; nobody should memorize an IP at a sound check.
  • "Mobile first, then tablet" — ship the phone layout first; the same binary becomes a two-pane stage-manager console on tablets.
  • Terms carried over from the desktop app: setlist (ordered songs), live output (what's projected), Output 1 / Output 2 / Stage, join code (the 6-digit LAN pairing code).
  • Visual direction: the app adopts the JEMO CORE monochrome look — black fill, white text, hard borders. It matches the brand and it's readable in a dark sanctuary.

Phases

Phase 1Server discovery beacon
  • Add bonjour-service; publish _lyricdisplay._tcp.local on the existing listen host/port with TXT {name, ver}.
  • Name defaults to hostname ("LyricDisplay — SoundDesk"), overridable via LYRICDISPLAY_MDNS_NAME.
  • Unpublish cleanly when the process exits; tolerate failures (some Linux boxes lack multicast) without breaking startup.
  • Document the beacon in API.md.

Verify: start the desktop app, run avahi-browse -rt _lyricdisplay._tcp (or Bonjour Browser on macOS/Windows) from another machine on the LAN — the server shows up with the right port. Desktop regression: normal connect flow still works.

Phase 2Flutter scaffold + REST client
  • Create mobile/ Flutter project; wire the black/white M3 theme.
  • Model classes mirroring buildCurrentState()'s payload and the setlist item shape from server/events.js.
  • api_client.dart: typed methods for status, setlist ops, lyrics next/prev/goto, output toggle, bible search/reference — all sending the stored Bearer JWT.
  • Cleartext network security config scoped to private ranges (the LAN API is plain HTTP; this trips everyone eventually).

Verify: unit tests against mocked dio cover every endpoint method and error mapping (401, 403, 423). flutter analyze clean.

Phase 3Connect flow
  • Bonsoir browse screen: list discovered servers, tap to select.
  • Manual entry fallback (host:port) on the same screen — guest-WiFi isolation kills mDNS more often than people admit.
  • Join code prompt → POST /api/auth/token with clientType: "mobile" → JWT into flutter_secure_storage.
  • Handle 423 lockout with a clear countdown message; handle expired tokens via /api/auth/refresh, re-prompt for join code if the server restarted with a new one.

Verify: on-device test against a running dev server: discover → pair → token persists across app restarts; wrong code five times triggers the lockout screen; restart server → app detects invalid join code and re-prompts.

Phase 4Live control core
  • socket_service.dart: connect with auth token, request requestCurrentState, subscribe to currentState, lineUpdate, setlistUpdate, outputToggle, individualOutputToggle, authError.
  • Riverpod providers turn those broadcasts into reactive UI state.
  • Live screen: song title, all lines with current line highlighted, next-line preview, transport bar (prev/next/jump-to-line), master live-output toggle plus per-output switches.
  • Commands go out over REST; state comes back over sockets — one write path, one read path.
  • Auto-reconnect with exponential backoff; banner when disconnected.

Verify: phone and desktop connected simultaneously — tapping next on the phone moves the desktop preview instantly, and vice versa. Kill/restart the server: app reconnects and resyncs without manual action.

Phase 5Setlist management
  • List view with drag-reorder, load-on-tap, swipe-remove.
  • "Add song" sheet: paste txt/lrc content + name → POST /api/v1/setlist/add. No file picking in v1.
  • Clear-setlist behind a confirm dialog — destructive actions get friction.

Verify: reorder/add/remove/load from the phone reflect in the desktop setlist within one beat; desktop-side changes appear on the phone via setlistUpdate.

Phase 6Bible quick search
  • Search field → GET /api/v1/bible/search, results list, tap loads the reference as slides.
  • Show which translation is active (GET /api/v1/bible/list).
  • Graceful empty state when no Bibles are loaded on the desktop.

Verify: search a known reference on device, load it, slides advance on desktop correctly.

Phase 7Tablet adaptive layout
  • LayoutBuilder breakpoint: <600dp keeps bottom-nav phone layout; ≥600dp renders the two-pane console — left pane tabs (setlist / bible), right pane live view + transport, always visible.
  • Landscape phones keep the phone layout; foldables just cross the threshold naturally.
  • Haptic feedback on transport taps; oversized touch targets for use while standing at a sound desk.

Verify: run on a tablet emulator (or foldable posture) — split view renders, both panes stay live during a service-flow dry run; no horizontal scroll at any supported size.

Phase 8Hardening & release
  • Edge sweep: token expiry mid-service, join-code rotation, server killed mid-song, airplane-mode recovery, backgrounded socket resume.
  • Integration test script: boots dev server + runs driver against it (documented, manual-friendly).
  • Build signed release APK; README instructions for install + pairing.

Verify: full dry-run on real hardware — discover, pair, run a 5-song set end to end without touching the desktop. Release APK installs on a clean device.

Risks & Honest Caveats

  • mDNS can be blocked (guest WiFi, AP isolation, some routers). The manual-entry fallback isn't optional — it's the safety net, and it stays one tap away forever.
  • Cleartext HTTP on Android: the LAN API has no TLS. Scoped network security config keeps this deliberate instead of accidental. Token theft risk on a hostile LAN exists today even for the web client; the join code is the gate.
  • Join codes rotate on server restart — the app must treat authError as "re-pair", not crash. Handled in Phase 3.
  • Server state is in-memory (snapshotted to JSON). Nothing for the app to do about that; it just means the app is a pure client — no offline queueing in v1. If you tap next while offline, it fails visibly and state resyncs on reconnect.
  • iOS builds are unverified until someone runs them on a Mac with signing set up. The codebase won't fight it, but I haven't measured it.

Out of Scope (v1)

  • Song authoring/editing from the phone.
  • Background media upload and per-output styling.
  • Stage-display messaging and timers.
  • Multi-server profiles beyond "last connected".
  • iOS store release.
