LyricDisplay 6.9.0 · Implementation Plan · September 2026

Live Sermon Assist

Transcribe the pastor live and turn what he said into tappable suggestions inside LyricDisplay: the next lyric line, the Bible verse he just quoted, a running sermon note. The model is never part of the app. It lives in a separate engine process the user installs only if they want it, or skips all of it and uses a cloud provider. Zero bytes, zero dependencies, zero microphone access until they say yes.

The target hardware is capable, so the default is the best model, not the smallest — and because guessing wrong wastes a whole model download, the app can benchmark the real candidates on the real machine and show measured word error rate, real-time factor, GPU utilisation, and load time before anything is adopted.

The Verdict

Build this as one thin client and one replaceable engine. The app grows a SpeechEngineClient, a settings section, and a suggestion rail. It gains zero new runtime dependencies and zero model files. Everything that knows about weights — downloading them, loading them, running them, killing them — lives in a standalone speech-engine/ process that is not in the installer, not in package.json, and not in git.

The cloud switch is the part most people get wrong, so it is worth being blunt: cloud is not the engine's job. Cloud is an HTTPS call, and the app already ships an HTTPS proxy on 127.0.0.1:4000 with keytar-backed secrets. If cloud transcription required installing the engine plugin, then "switch to cloud" would not be a switch, it would be a reinstall. So local models go through the plugin; cloud goes through the backend the app already runs.

1. Reading Your Request

Your brief had four moving parts and a lot of room to misread. Here is exactly how each phrase was interpreted, so you can correct me before a line of code is written.

You said

"shows suggest of thing the pastor said in ui"

The word suggest is doing the real work here. If you wanted captions you would say captions. This is a co-pilot rail: the app listens, and offers ranked, one-tap actions — never a wall of text, and never anything the congregation sees until you press send.

Three suggestion lanes ship, in this order of value:

  1. Next lyric line — he is preaching over a song or reading a passage; match the transcript tail against the loaded lyrics and jump the highlight. Highest value, zero new output code.
  2. Bible verse — he says "first Peter, verse five" or quotes a line; resolve the reference and offer the verse for one-tap display. This is the part you asked about explicitly, and the app already has 90% of it.
  3. Sermon note — an accumulating draft that lands in the existing Free Note mode when the service ends.

A fourth lane — he said the title of a hymn, pull up the song — is a natural fit and is listed as a stretch in Phase 8, not a promise.

You said

"i do not want to be installed in the app by default"

Read strictly and enforced mechanically, not by convention. Six testable invariants in section 5, each backed by an automated test that fails CI. This is the constraint most likely to erode over eighteen months of ordinary feature work, so it gets a test rather than a README note.

The pre-existing ExperimentalSection in src/components/UserPreferencesModal.jsx (around line 1112; verify at implementation time) already models exactly this pattern — off by default, hidden from the interface, opt-in, toast on enable. The new feature follows that precedent exactly.

You said

"choose what local model i want the size"

This is a first-class settings surface, not a hidden config. A catalog table with real download sizes, real RAM cost, real quantization, a one-click benchmark on the user's own machine, and a resumable downloader. Sizes are not estimates — they are the published upstream figures for whisper.cpp GGML, tabulated in section 8. The user's hardware is capable, so the default is the best model and size anxiety is gone; the ability to choose down is a convenience for weak machines, not the expected path.

You said

"plugin or another application when ran the model and other in there but the model setting and suggest will be in the app itself"

This is the load-bearing architectural sentence, and it is exactly right. It splits the feature cleanly:

  • Out of process: model weights, the inference runtime, the binary, the downloader, the process lifecycle.
  • In the app: every control, every setting, every suggestion, every button, all live state, all history.

The user never sees the plugin. They see a settings page and a suggestion rail. The plugin is infrastructure, not a user-facing product. This is a good instinct — resist any future urge to surface "engine" jargon in the operator UI beyond a one-word status chip.

3.1 Where the engine runs

Path A has two placements, and this is the single most useful thing to get right about the whole design: a remote engine is a transport change, not a second contract. Only text crosses the network — a few hundred bytes per second of transcript and suggestion events — so moving the model to another machine changes how the app dials the engine, and nothing else. There is no second protocol, no second suggestion engine, no second set of settings.

Why Mode C is the best deployment and the plan nearly missed it

Running the model in the sound booth and sending only text to the control room is the cleanest version of this feature, and it dissolves the hardest problem in it. The single most dangerous failure for a live service is inference saturating the operator machine while OBS, vMix, and two output windows are running. In Mode C that cannot happen, because the operator machine never runs the model at all.

It also improves capture quality for free: the engine sits next to the wireless receiver and takes the signal before it has travelled through a mixer, a USB interface, and a Windows resampler. The cost is a second machine and a pairing step, which is why it is opt-in and later rather than the default.

The church LAN is not a trusted network

This is the thing that makes Mode C a security decision rather than a networking convenience. During a service, congregants are on the church WiFi. A laptop in the third row is an untrusted machine on the same network as the booth engine. So Mode C requires: the token from section 7.1 to be mandatory rather than merely good practice; an explicit opt-in before the engine will bind anything other than loopback; a visible Remote engine indicator whenever the app is talking across a network; and a session key the user can see and revoke. A LAN engine that accepts anonymous connections during a service is not a convenience, it is a way for a visitor to put words in a pastor's mouth on the screens.

Why the renderer captures the microphone

The obvious alternative is to let the engine open the audio device itself. Do not. Cross-platform input capture is a tar pit: Windows needs WASAPI, macOS needs CoreAudio and TCC permissions, Linux needs PulseAudio or PipeWire monitor sources, and whisper.cpp ships no microphone code at all. The browser already solved this problem portably, and the control-panel renderer is a long-lived window that is always open during a service.

The engine stays a pure compute process: bytes in, text out. That is a much smaller contract, far easier to test, and it means a third-party engine can be written in any language.

Why fan-out goes through main, not straight to the renderer

The engine pushes transcripts with process.send() to main, and main re-emits over webContents.send. This matches how lyricWatcher, fileNavigator, and recents already work, it means one fan-out point for multiple windows, and the transcript log survives a renderer WebSocket drop. The renderer-to-engine WebSocket is strictly one-way audio ingest plus acknowledgements.

4. Decision Log

Eleven decisions that shape everything downstream. Each records what was chosen, why, and what was given up. If you disagree with any of these, say so now — each one is expensive to reverse after Phase 2.

D1

Cloud does not run through the engine

Chosen: local inference in the plugin; cloud as an HTTPS proxy in server/, which the app already runs.

Why: if cloud required the plugin, "switch to cloud" would be a reinstall, and the whole point of the cloud option is to be the path of least resistance. The user's constraint was about models; an HTTPS client is not a model. It also keeps API keys in secretManager.js on the backend rather than in a renderer or a third-party process.

Given up: two ingest implementations. Mitigated by sharing one PCM frame format and one normalizer behind a single interface.

D2

WebSocket for engine audio, Socket.IO for cloud audio

Chosen: a raw ws://127.0.0.1 WebSocket to the engine; a binary emit on the app's existing Socket.IO connection to the backend.

Why: both are zero-dependency in the renderer — Chromium ships native WebSocket, and socket.io-client already carries binary frames. Inventing a third transport would be pure cost.

Given up: two mental models. Both are fire-and-forget binary up / JSON down, so the senders are near-identical.

D3

The app spawns the engine only after the user installs it

Chosen: a discover-then-spawn lifecycle. The app probes a well-known path under userData; if the engine is absent, nothing starts and the feature stays visibly off.

Why: a fork on every launch of an optional component is the classic way an "optional" feature quietly becomes mandatory — one crash-loop and startup now depends on something the user may have deleted.

Given up: slightly more code in the supervisor than a blind fork. About forty lines.

D4

The catalog is static JSON in shared/; the weights are not

Chosen:shared/speech/models.catalog.json ships with the app. ggml-*.bin files are downloaded on demand to userData/speech-models/ and are never in the repo or the installer.

Why: the user must be able to see the full menu of choices before deciding to install anything, and be able to compare them on their own machine rather than take the app's word for it. A catalog of four kilobytes of metadata is the minimum that makes "choose your model" a real choice. shared/**/* is already in the electron-builder files list, so the catalog ships for free.

Given up: the catalog can go stale. Mitigated with a version field and a remote-refresh that is opt-in and never automatic. Benchmarked results are stored per machine and per engine version, so a stale catalog never invalidates a measurement the user already has.

D5

Suggestions are suggestions, never auto-displayed

Chosen: a suggestion populates a staging area. Only an explicit press sends it to an output.

Why: this is worship software. Putting an unverified machine transcript of a pastor's words on the sanctuary screens without a human pressing a button is not a feature, it is a liability. A wrong verse on the wall during a service is a far worse outcome than the operator typing it.

Given up: the "wow" of a fully automatic display. Worth it, every time.

D6

No cloud provider SDKs. Plain fetch and FormData.

Chosen: hand-rolled request/response adapters in server/ using globals that exist in Node 18+.

Why: official SDKs are heavy, frequently pull in transitive dependencies that break on a fresh machine, and abstract away exactly the request shape you need to control. These five APIs are stable and trivially hand-written.

Given up: automatic handling of new provider models. Irrelevant — transcription API surfaces barely move. One explicit ws dependency is added to server/package.json if streaming providers are enabled; it is declared directly, never relied on transitively via socket.io.

D7

The engine is a separate release, not a subfolder of the app

Chosen:speech-engine/ lives in this repo as a self-contained package with its own package.json, its own tests, and its own version. Its binaries ship as GitHub release assets. The app downloads a pinned release on demand.

Why: it makes the "not installed by default" guarantee structural rather than aspirational. Phase 7 takes this from independent source layout to independent release — separate tags, separate manifest, separate workflow, and no app build required. If the engine were a workspace dependency, a single careless npm install would merge it into the app. A separate release with a checksum means the app can verify what it fetched, and the engine can be updated without shipping a new app build.

Given up: one more release train to operate. It also means the engine must obey a compatibility contract, which is the point.

D8

Model selection is measured, not recommended

Chosen: a benchmark harness that runs real models against a real reference clip on the user's own machine and reports WER, RTF, compute backend, GPU utilisation, load time, peak memory, and thermal decay. The app recommends the fastest model within a stated margin of the best measured WER.

Why: every other answer here is a guess dressed as a recommendation, and two guesses fail badly. Silent CPU fallback makes a capable machine look slow and sends the user hunting for a model problem that does not exist. Thermal decay lets a laptop pass a quick test and then fail at minute 25 of a service. Both are invisible to a spec-based recommendation and obvious to a measurement. The hardware here is capable, so measuring is cheap — a few minutes, once — and it is the difference between an informed choice and a coin flip.

Given up: nothing, in dependencies. WER reuses the Levenshtein already in main/lyricsProviders/searchAlgorithm.js, extracted to shared/wer.js. Adding an evaluation library to compute the metric would be self-defeating in a plan whose premise is adding zero dependencies.

D9

Transcript history on by default, with lighter cloud ceremony

Chosen: local transcript persistence defaults on. Cloud selection carries a single accurate, always-visible mode indicator and nothing more — no modal, no acknowledgement gate, no default-on upload block.

Why: the sermon is published to the church's own YouTube channel, so the transcript is not a secret. An earlier draft treated local persistence as a risk requiring opt-in and wrapped cloud upload in a consent flow. That was wrong twice over: it flagged a non-risk, and a warning that appears on every run is a warning people learn to dismiss. The one real distinction is that the live feed contains audio absent from the published recording — anything off-mic, any service not streamed — which is a one-line honest reason to keep local as the default and a clear mode indicator as the entire safeguard.

Given up: defensiveness for a ministry that streams everything, in exchange for not training operators to click past warnings. Unchanged: disk caps, erase-on-uninstall, and a hard rule that no audio or transcript content ever reaches the app log — that last is hygiene, not ceremony.

D10

“Local” is two axes: where it runs, and which provider does the work

Chosen: three independent selectors — where (this device / a device on this network / the cloud), who (the provider), and which model (the weights) — with the model list filtered by the chosen provider.

Why: collapsing “local” into a single toggle is the mistake that makes a settings surface unusable. A user who wants everything on their own hardware is asking two unrelated things: whether the machine is across the room, and which local runtime does the work. The moment those share one control, the second question has nowhere to live and the provider catalog never ships.

Given up: a little more settings code and a compatibility matrix to maintain. That is cheap, and the alternative is permanently binning together two unrelated decisions.

D11

The provider is invisible to the app, which is what makes the catalog safe to extend

Chosen: every local provider is an implementation of the same v1 contract. The app holds a SpeechEngineClient and never learns whether it is talking to whisper.cpp, sherpa-onnx, Vosk, a platform API, or something a user wrote themselves.

Why: this turns adding a provider into a data change rather than a code change, and it is why the plan can promise an “any local runtime” escape hatch without shipping a plugin marketplace. It is also the only reason a weaker provider can be handled honestly: capabilities arrive in /v1/health, so the app can disable a lane and say why instead of quietly producing worse suggestions.

Given up: the app cannot optimise for a provider it does not know about. Accepted — a provider that fails to report its capabilities gets the conservative default behaviour, which is the right direction for that failure.

5. The Not-Installed-By-Default Guarantee

Six invariants. Each one gets an automated test. Any PR that violates one fails CI. This is the mechanism, not the intention — intentions decay, tests do not.

1. Zero bytes in the installer

A test parses package.json's build.files, asarUnpack, extraResources, and extraFiles and fails if any pattern can match speech-engine or a weights file.

2. Zero new root dependencies

A test snapshots the root dependencies object. A diff fails the build. Whisper bindings, ONNX runtimes, and transformers.js are all explicitly banned by name.

3. Zero weights in git

/speech-engine/models/, *.bin, *.onnx, and *.gguf are gitignored. CI fails on any tracked file over 20 MB.

4. Off by default, cold by default

speech.enabled defaults to false. With the default state, no process is spawned, no permission is requested, no socket event is emitted, and no network request is made. Asserted in a boot smoke test.

5. Audio stays local unless cloud is chosen

The engine binds 127.0.0.1 only and rejects non-loopback peers. The cloud path is reachable only after a provider, a stored key, and an explicit acknowledgement that audio leaves the machine.

6. Uninstall is real

A single action removes the engine directory, every model file, the transcript history, the benchmark results, and the stored key, and reports the bytes reclaimed. With history on by default this matters — a shared church laptop is not a private machine, and the user should not have to hunt for leftovers.

The one place this rule is deliberately bent

shared/speech/models.catalog.json does ship in the installer, because shared/**/* is already an electron-builder include and the catalog is roughly four kilobytes of text. It contains names, sizes, and URLs — no weights. A test asserts the catalog contains no field whose value exceeds the text size of the file itself, which keeps "metadata only" from quietly becoming "a little bit of model".

7. The Engine Contract

A small, stable, versioned surface. The app is written against this and nothing else. Any engine that implements it — in any language — works.

7.1 Transport and security

Co-located engines are loopback-only. A Mode C engine (section 3.1) is not, and the difference is the whole security story.

  • Engine binds 127.0.0.1 on an OS-assigned ephemeral port. Never 0.0.0.0.
  • At spawn, main generates a 32-byte random token, passes it via environment, and requires it as an x-ld-speech-token header on REST and a query parameter on the WebSocket upgrade.
  • The engine rejects any peer whose Origin is not http://127.0.0.1:4000 or http://localhost:5174. This blocks a random web page in the operator's other browser tab from driving the engine.
  • Token is rotated on every spawn. A stale token is a dead engine, not a security hole.
  • Mode C only: the engine binds 0.0.0.0 (or a chosen interface) only when the user explicitly enables LAN mode. The default is loopback, always.
  • Mode C only: a session key is shown in the UI, rotatable and revocable, and the engine advertises via mDNS as _lyricdisplay.speech._tcp — following the pattern already proven in server/mdnsAdvertiser.js for _lyricdisplay._tcp. Discovery is a convenience; the token is still mandatory.
  • Mode C only: the payload is text only. No audio, no model weights, and no Bible content ever crosses the LAN.

7.4 Latency and endpointing

  • Emit a partial roughly every 600 ms of new audio.
  • Emit a final on 500 ms of detected silence, or on a 15 s hard cap.
  • Target for first partial: under 1.2 s locally, under 800 ms on cloud. These are acceptance criteria, measured in Phase 3, not claims.
  • If the measured target is missed on the user's hardware, the settings page says so plainly and recommends a smaller model. It never silently degrades.

7.5 Versioning

The health response carries apiVersion. The app refuses to talk to a mismatched major, warns on a mismatched minor, and ignores unknown fields. That “ignore what you do not recognise” rule is what makes section 12 possible: it is the reason a compatible engine can ship without an app release, and the reason contract minor bumps are additive-only rather than a matter of discipline.

9. The Benchmark Harness

The user runs this on their own machine, on real audio, and gets real numbers. It replaces every guess in this plan with a measurement, and it is the reason the model catalog is a table with a Run button rather than a list of opinionated recommendations.

9.1 Why this earns its place

Two problems it solves that nothing else does. First, silent CPU fallback: whisper.cpp binaries drop to CPU without announcement, and a user then believes the model is slow when their GPU sat idle. Second, transcription quality is not predictable from parameter count on domain audio — the accuracy gap between a quantised medium and a full large-v3 on a reverberant room with an accent is not derivable from a table, it is measurable, and the user already has the hardware to measure it on.

It is also the honest answer to "which model should I pick" in a way a dropdown never is. The app can show that large-v3-turbo-q8_0 scores within noise of large-v3 on the reference clip while running four times faster — in which case the 2.9 GB download is a waste — or that it does not, in which case the fast pick is a bad trade. Either answer is useful, and neither is available without running it.

9.2 The reference clip

A fixed 90-second audio clip with a hand-verified ground-truth transcript, shipped as a separate small download on the engine's install step. It deliberately sounds like the target domain: a single voice, moderate reverberation, one non-native accent, no music.

  • Licensed for redistribution, stored as Opus at roughly 1–2 MB, verified by checksum like any other engine asset.
  • Not bundled in the app. Like every other engine artifact, it is fetched during engine install, keeping the app at zero bytes.
  • Can be replaced with a clip of the church's own pastor for a genuinely local measurement, which is the highest-value option and a natural Phase 9 addition.

The switch you asked for. Same PCM in, same rail out, different hop on the way to the model. All handled in server/ with plain fetch and FormData.

On the privacy framing — adjusted

An earlier draft of this plan treated cloud upload as a heavyweight consent problem. That was wrong on the merits. The sermon is published — it goes out on the church's own YouTube — so the content of the transcript is not a secret, and treating it as one produces a consent flow that trains users to click through warnings without reading them. Warning fatigue is worse than no warning.

11. The Suggestion Engine

Where the transcript becomes something useful. Pure functions, no I/O, fully unit-testable.

Lane 1

Next lyric line

Fuse.js over useLyricsStore().lyrics using the last 8–12 words of the transcript tail, with a threshold below which nothing is suggested. Returns the top three with scores. The rail shows the current line, the match, and the line after it, because the operator's actual question is "where do I go next", not "what did he just say".

Send action: sets selectedLine through the existing path. No new output code at all.

Lane 2

Bible verse

Three detectors, tried in strict order, because the first is far more precise than the second and the second far more precise than the third. (1) Spoken-form normalisation. A pure function converts number words to digits and ordinals to book numbers, then feeds the reference regex that already exists at shared/bible/index.js:148 (REFERENCE_REGEX). This is the highest-value and most skippable piece of the whole detector, because a pastor almost never says the digits: "John chapter three verse sixteen" → John 3:16, "first Peter five" → 1 Peter 5, "forty two" → 42, "Psalms twenty three" → Psalm 23:1. Spoken ranges too: "sixteen through eighteen" → 16–18. (2) Phonetic and confusion matching. A static data table in shared/bible/bookAliases.js mapping the book names the model reliably mishears onto the correct ones. This is not a nice-to-have — it is where most of the real-world errors live, because these names are rare in training data and phonetically ambiguous. No dependency, no fuzzy-matching library, just data, and trivially unit-testable. (3) Full-text fuzzy match of the transcript tail against verses in the active translation, using the existing src/utils/bibleSearch.worker.js off-thread pattern so a 30,000-verse search never touches the UI thread during a service. Nothing, when none of them fire.

If a summary is ever wanted, it belongs behind the same engine contract as an explicitly enabled capability, not assumed.

Hallucination is a correctness problem here, not a performance one

Whisper given silence, room tone, or non-speech fabricates plausible text. Its signature is a short phrase repeated — "Thank you. Thank you. Thank you." — which is harmless in a general transcription tool and actively dangerous in this one. A hallucinated "John 3:16" does not arrive as noise. It arrives as a clean, correctly-formatted, high-confidence Bible verse suggestion, one tap from the sanctuary screens. That is the single worst failure this feature can produce, and it is why VAD is a correctness requirement rather than a performance optimisation.

  • Energy gate before inference. Never submit a segment whose peak or RMS is below a noise floor. Cheap, and it removes most of the problem at the source.
  • Reject on the model's own no-speech probability. Whisper reports no_speech_prob per segment. Above a threshold, the segment is discarded outright and no suggestion is ever generated from it.
  • Repetition detector. A segment whose tail repeats an identical short phrase is discarded. This catches the cases the energy gate misses, such as a fan or a chair scraping.
  • The confidence gate applies to the segment, not just the match. A perfect verse match built on a segment the model itself flagged as noise is not a 98% match. Confidence is multiplied by segment confidence before it reaches the card.

Hotword biasing makes this worse, and the interaction is easy to miss

The hotword bias described below feeds the loaded song's lyrics in as a decode-time prompt, and it is the single biggest accuracy win for hymn titles. But a bias prompt is also a suggestion: given silence, a biased decoder is more likely to emit the biased text, not less. So the two features fight each other. The resolution is that the VAD gate runs first and biasing is applied only to segments the VAD actually opened. A segment of room tone never reaches the decoder, so it can never hallucinate a lyric. Get this ordering wrong and the hotword feature will confidently suggest the previous verse at the moment the pastor stops speaking — which is exactly when the operator is least suspicious.

Sermon profile — the cheap trick that makes accuracy usable

Church audio is hard: reverberant rooms, lapel mics clipping, accents, and hymn titles the model has never heard. Two cheap, high-leverage mitigations that cost nothing and are not part of the model choice at all:

  • Hotword biasing. Feed the currently-loaded song's lyrics, plus a user-editable proper-noun list (the pastor's name, the church's name, denominations), as a decode-time bias prompt. When the loaded song is Amazing Grace, the transcript reliably says amazing grace instead of amazing grace's mangling. This is the difference between a demo and something a church can rely on, and it is free.
  • Level discipline. A live VU meter with a clipping indicator, so the operator positions the lapel mic once, correctly, instead of guessing. Most bad transcripts are a bad input signal, not a bad model.

12. The Separate Release Pipeline

The engine must ship on its own cadence. An app release is expensive — electron-builder, three platforms, Windows signing, macOS notarisation, a hundred-megabyte installer — while whisper.cpp cuts releases weekly. 12.3 The release action

A dedicated GitHub Actions workflow in the speech-engine/ directory of this same repo, with its own tag namespace (speech-engine-v*) so engine tags never collide with app tags. It runs on a version tag or a manual dispatch and does exactly this:

  1. Build the engine for the five target platforms in a matrix.
  2. Package each as a self-contained bundle — runtime, contract shim, and nothing else.
  3. Compute a SHA-256 per asset and emit releases.json with the manifest above.
  4. Publish a release with all assets and the manifest attached.
  5. Optionally sign assets, so a compromised release cannot be silently substituted.

Critically, this workflow shares no steps and no cache keys with .github/workflows/build-release.yml or build-on-push.yml. Sharing them is how a fast engine release ends up blocked behind a slow mac notarisation queue — the exact coupling this phase exists to remove.

Same repo, separate release — and why not a separate repo

The engine lives in this repo as a self-contained package with its own package.json, its own tests, and its own version. That was decision D7. This phase makes the release independent too, which is a separate axis.

A truly separate repository buys independence the pipeline already provides, and costs the one thing that matters most here: a single, reviewable home for the contract. In one repo the contract, the app client, the fake-engine fixture, and the conformance suite sit together and cannot drift. Independence of release cadence is what was wanted; independence of source control is not, and it would make every contract change a two-repo dance.

12.4 The update path inside the app

  • Check is manual, install is prompted, silent update is never. The user installed this component deliberately; silently replacing a binary they chose is presumptuous, and a bad silent update is precisely how trust in an optional component is lost. An Update available badge appears, and the user clicks.
  • The check is gated on speech.enabled. This is what keeps invariant 4 in section 5 true — with the feature off, the app makes no network request of any kind, including to the manifest.
  • Staged then swapped. Download to a temp directory, verify SHA-256, then move into place using the crash-safe write helper already in main/atomicFileSave.js. The running engine keeps its current binary until it is restarted, so an update never interrupts a service in progress.
  • Health-check rollback, and this is the important one. After a swap, the new engine must pass a health check within a timeout. If it does not, the app silently reverts to the last known-good version and tells the user in one line. A bad engine release that leaves a church with no transcription at all is a far worse outcome than being a version behind.
  • Model files are never touched by an engine update. Weights are keyed to the catalog, not the engine version, so a 2.9 GB download survives every engine upgrade.
  • Beta channel is opt-in per machine and visibly labelled, never the default.

Offline and air-gapped installs

Churches with poor or no internet are a real and common case, and the whole feature is useless to them if it only installs online. The release therefore ships a single portable bundle plus a documented drop-in path — unpack it into the engine directory and the app finds it on next launch through the same discovery it already uses. The installer and the manifest both work fully offline; nothing in this design requires reaching GitHub to run.

13. Phases

Eleven phases. Phases 0–3 and 5 are the shippable feature. Phase 4 is what makes the model choice measured instead of guessed. Phase 7 makes the engine ship independently of the app, with its own tags, its own manifest, and no app release in the critical path. Phase 6 is what makes the cloud switch real and what decides whether a church can trust this on a Sunday. Phase 8 puts the engine on a dedicated booth machine. Phases 9–10 are breadth and packaging. Every phase ends with the app in a shippable state — there is no phase that leaves the tree broken.

Phase 1

Audio Capture — and the Two Blockers

Do

  • session.setPermissionRequestHandler + setPermissionCheckHandler in main, granting media on the control window's webContents only. Output, stage, and dynamic output windows are denied.
  • build.mac.extendInfo with NSMicrophoneUsageDescription, plus NSAudioCaptureUsageDescription for macOS 14.2+ aggregate devices.
  • src/workers/pcmWorklet.js — AudioWorklet requesting { sampleRate: 16000 }, with a manual decimation fallback if the context rate is refused.
  • Audio source model, before any UI. A “device” here is not necessarily a microphone. It can be a lapel mic, a USB interface, a line-in, a loopback monitor source, or a network source such as Dante, AES67, or a Discovery-based multicast feed from a digital mixer. The picker groups them by kind and does not assume a local hardware input exists. A church feeding a digital console over the network is a normal deployment, and building the model around local interfaces makes it unsupported by accident.
  • Device picker via enumerateDevices, and the label trap is the first thing to handle. Chromium returns every device with an empty label until getUserMedia permission has been granted at least once, so a naive picker renders a dropdown of blank rows on first run — which is exactly the first run. The order is therefore fixed: request permission, then enumerate, and never build the list before permission resolves. If permission is denied, the list shows a single explanatory row naming the fix rather than a set of empty ones.
  • Loopback and monitor sources called out by name, because users do not know to look for them: Windows Stereo Mix and What U Hear, macOS aggregate devices and BlackHole, Linux PulseAudio and PipeWire monitor sources, plus any network source the platform enumerates.
  • Remember the choice. The selected source persists per machine in useSpeechStore, keyed by a stable identity rather than by index, because device ordering is not stable across reboots. On launch: use the remembered source if it is still present; if it has disappeared, say so in one line and fall back to the system default rather than silently opening something else. A church laptop that moves between rooms should not have to re-pick every Sunday.
  • Handle devicechange. Live enumeration on connect and disconnect, and when the active source vanishes mid-service, raise an explicit re-pick affordance in the rail instead of leaving a dead dropdown and a flat meter. The failure mode to avoid is a device dying at minute 20 with nothing the operator can act on.
  • A “test this source” affordance next to the picker: three seconds of level metering without arming transcription, so the operator can find a working input before the service rather than during it.
  • Live VU meter with a clipping indicator and a device-health line that says the honest thing when the chosen input is clearly wrong.
  • useAudioCapture hook owning arm, mute, stop, and teardown. Teardown is the interesting part: a stuck mic after the window closes is the kind of bug that loses a church's trust permanently.
  • Panic stop hotkey, and an unmute-on-launch guard that requires a deliberate user action rather than arming itself.

Exit criteria

Meters show real levels from a lapel mic, from a line-in, from a loopback monitor source, and from a network source. The picker shows real device names on a first run with no prior permission, and never a list of blank rows. A remembered source that has disappeared produces one clear line and a stated fallback, not a silent switch. A source that vanishes mid-service raises a re-pick affordance. Denied permission, no device at all, and output-window-loads are all handled without a dialog or a crash. No frame is ever sent anywhere. DevTools confirms a closed AudioContext leaves no live track.

Phase 3

Benchmark — Choosing the Model With Numbers

Benchmarking the catalog on the reference clip produces a stable, repeatable table. The same model benchmarked twice gives a WER within noise. The recommendation follows the measured knee, not the default. A CPU-only machine is told so plainly and given the specific fix. Benchmarking while an output window is rendering is refused rather than allowed to stutter.

A 20-minute recorded service transcribes end to end; the next-lyric suggestion is usable throughout; a spoken reference produces a correct verse card; and every send action moves the real output. Phase 5

Cloud — the switch you asked for

  • server/speech/ — provider adapters, a shared PCM ingest endpoint, and partials emitted over the existing Socket.IO channel.

Phase 6

Live Safety & Reliability

The phase that decides whether this is used on a Sunday or abandoned after one bad rehearsal. Treated as a first-class deliverable, not a cleanup pass.

Do

  • CPU and memory guardrails: shed to a smaller model or drop to batch mode if the engine exceeds a threshold, and never let inference starve the output renderers. Output frame rate is the priority, full stop.
  • Auto-suspend if an output window or the socket connection fails, so a crash does not silently take the mic with it.
  • Disk cap with rotation on transcript history, and a hard cap that stops recording rather than filling the church's drive.
  • Redaction: no raw audio ever written to the app log; transcripts are excluded from log forwarding by default.
  • Engine watchdog: unresponsive engine is killed and respawned at most twice, then the feature disables itself with a clear message instead of thrashing.
  • A 90-minute soak test with a realistic mix of speech, silence, and music, asserting zero output frame drops and bounded memory.
  • One-click full erase of engine, models, history, and keys.

Exit criteria

The soak test passes with no output frame drop. Killing the engine mid-service leaves the app fully usable and says what happened. Disk usage is bounded and reported.

Phase 7

Separate Release Pipeline — Engine Ships on Its Own

Ordered before Engine Breadth on purpose. A second engine cannot be released independently until this pipeline exists, so this is a dependency, not a packaging detail.

Do

  • Split versioning into three numbers — contract api, engine version, app version — with the additive-only rule for contract minor bumps enforced in code, not convention. The app ignores fields and message types it does not recognise.
  • minAppVersion on every engine release, checked at discovery so an incompatible pair is refused with a sentence a human can act on rather than a mystery failure.
  • A dedicated GitHub Actions workflow under speech-engine/, triggered by a speech-engine-v* tag or manual dispatch. Matrix build across win-x64, win-arm64, mac-x64, mac-arm64, linux-x64.
  • Per-asset SHA-256, an emitted releases.json manifest, and a published release carrying both. Optional asset signing.
  • Explicit isolation from the app's own workflows — no shared steps, no shared cache keys — so a fast engine release is never queued behind a slow notarisation.
  • App-side updater: manual check, prompted install, no silent update, and the check gated on speech.enabled so invariant 4 in section 5 still holds.
  • Staged install with SHA-256 verification and an atomic swap via the existing main/atomicFileSave.js helper. The running engine keeps its binary until restart, so an update never interrupts a service in progress.
  • Health-check rollback: a new engine that fails its post-swap health check is reverted to the last known-good version automatically, with one line of user-facing explanation.
  • An offline portable bundle plus a documented drop-in install path, and a full offline install path written into INSTALLATION.md.
  • Model files are never touched by an engine update, so a 2.9 GB download survives every engine upgrade.

Exit criteria

An engine-only tag produces a release with no app build, no app version bump, and no mac notarisation in the critical path. A compatible engine update installs cleanly on an app two releases old. A deliberately broken engine build is caught by the health check and rolled back with no loss of function. The whole install works with the network disconnected. Existing model files survive an engine upgrade untouched.

Phase 8

Mode C — Engine on a Dedicated Booth Machine

Depends on Phase 7. A second machine cannot have its engine updated independently until the release pipeline exists, and every update to a booth PC would otherwise mean reinstalling the app on the operator machine.

Do

  • LAN mode in the engine, defaulting to off. The engine binds loopback until the user explicitly enables a network interface, and the setting is worded so that turning it on is a deliberate act rather than a checkbox.
  • The session key becomes mandatory rather than merely defensive, and the token is checked on every request. No anonymous LAN operation, ever.
  • mDNS advertisement as _lyricdisplay.speech._tcp, mirroring the working server/mdnsAdvertiser.js pattern, with manual endpoint entry as the fallback for networks that block multicast.
  • A pairing flow: show the booth engine's key and address, let the operator enter them, and store the result in the existing keytar-backed credential store.
  • A persistent Remote engine indicator, so an operator always knows whether the engine is across the room or across the network.
  • Live connection health with an honest degraded state and one-click re-pair. A booth PC that rebooted mid-week must not present as a broken feature.
  • Reconnection that survives the engine restarting independently of the control room, because a booth machine may be rebooted at any time.
  • Written guidance on what does and does not cross the network: transcript text and suggestion events only — never audio, never weights, never Bible content.

Exit criteria

A booth machine pairs with the control-room app and drives real suggestions end to end. An unauthenticated client on the LAN is rejected. Killing and rebooting the booth engine mid-session recovers without operator intervention. And the operator machine loads no model in this mode — verifiable in the process list, which is the entire point of Mode C.

14. Testing

Contract conformance

A fake engine fixture implementing the v1 contract. The client is tested against it, so a protocol change breaks a test rather than a Sunday service.

Pure-function unit tests

Reference parsing, suggestion ranking, confidence thresholds, and confidence-gated suppression. Fast, deterministic, and where most of the real logic lives.

The six invariants

Automated, in CI, on every build. These are the tests that protect the constraint the user cared about most.

Store migration

SpeechStore version and migrate tested alongside the existing migratePersistedState suite, so a future schema change does not lose a user's model choice.

WER correctness

shared/wer.js tested against hand-computed cases: perfect match, substitutions, insertions, deletions, empty hypothesis. The benchmark's primary sort key has to be provably right or every conclusion drawn from it is wrong.

Benchmark determinism

The same model benchmarked twice yields WER within noise. If a metric is unstable it cannot be used to choose anything, and the UI must say so rather than presenting a noisy number as decisive.

Recommendation logic

Pure-function tests over synthetic result sets: picks the fastest model within the margin, refuses to recommend a model failing the RTF gate, and degrades honestly when nothing passes.

Version compatibility matrix

Every engine/api/app combination the manifest can express, tested against the client: compatible installs, major-mismatch refusal, minAppVersion refusal, and a malformed manifest. A release-pipeline bug must never be discovered as a crash on a user machine.

Rollback

An update to a deliberately broken engine is rolled back to the last known-good version automatically, and existing model files are byte-identical afterwards. If rollback itself is untested, it is not a safety net.

Spoken-form normalisation

The number-word and ordinal normaliser against a table of real phrasings: "chapter three verse sixteen", "first Peter", "forty two", "sixteen through eighteen", "the book of Acts". Pure function, fully table-testable, and the highest-value detector in the feature.

Phonetic confusion table

Every alias in bookAliases.js resolves to a real book, and no alias can resolve to two different books ambiguously without the surrounding chapter and verse disambiguating. Aliases are pure data, so this is a cheap test with a real payoff.

Hallucination rejection

Feed the engine synthetic silence, room tone, and a fan recording, and assert that no segment reaches the suggestion layer. This is the test that proves the worst failure mode cannot occur, so it matters more than any other test in the plan.

Mode C rejection

An unauthenticated client, a wrong key, and a wrong Origin are all rejected on the LAN interface. Pairing survives an engine reboot. And an assertion that the operator process list contains no model, which is the entire point of Mode C.

Provider conformance

One contract suite run against every provider implementation, plus a fake provider. Adding a provider without passing this suite is a CI failure, which is the mechanism that keeps the catalog from quietly rotting.

Capability gating

Assert that a provider reporting no word timestamps disables the lyric suggestion lane, that a provider reporting no bias support surfaces the degradation, and that neither fails silently. This is the test that makes D11 honest rather than aspirational.

Live smoke, opt-in

Gated behind LYRICDISPLAY_E2E_SPEECH=1 with a 30-second fixture in tests/fixtures/. Never runs in normal CI, never needs a microphone.

Device label trap

Enumerate before permission and assert the app does not present a list; grant permission and assert every row has a real label. This is the most common way a device picker ships broken and it is invisible on a machine that has already granted access once, so it needs a test rather than a manual check.

Source persistence and fallback

Remembered source present → selected. Remembered source absent → one clear line plus a stated fallback, never a silent switch. Identity is by stable key, not by index, so a reboot that reorders devices does not select the wrong input.

Hotplug mid-service

Unplug the active source while capturing and assert a re-pick affordance appears and the rail does not present a dead dropdown with a flat meter. The minute-20 failure is the one that matters.

Network source enumeration

Assert a network source is enumerated, grouped, and selectable without a local hardware input present, so a Dante or AES67 deployment is supported rather than accidentally excluded.

Audio teardown

A test that arms capture, tears it down five times, and asserts zero live MediaStreamTracks remain. The leak this catches is invisible in development and maddening in production.

16. Rejected Alternatives

Recorded so these do not get re-proposed in six months as though they were new ideas.

Run Whisper in the renderer with transformers.js or a WASM build

Rejected: it adds a large dependency to the default install, ships model-loading code to every user whether or not they want it, and puts a multi-hundred-megabyte model load on the same thread that renders the control panel.

This is the single most obvious approach and it contradicts the primary requirement. There is no version of it that satisfies "not installed by default".

Bundle the engine and a small model, hide the choice behind a toggle

Rejected: the requirement was explicit. A bundled small model is 31–466 MB in the installer, and a bundled engine is exactly the thing the user said they did not want.

Convenient, and directly contrary to the brief.

Let the engine open the audio device itself

Rejected: per-platform input capture is a tar pit and whisper.cpp has no microphone support at all. The browser already solved it portably.

Also splits the capture logic across two places for no benefit.

Route cloud transcription through the engine too, for symmetry

Rejected: it makes the cloud switch a reinstall, which defeats its purpose. Symmetry is not worth breaking the switch.

17. Open Questions

Four already answered, the rest carry a recommended default so none of them block Phase 0. They are ordered by how much they would cost to change later.

1. RESOLVED — How big should the default model be?

The target hardware is capable, so the default is large-v3 at 2.9 GB — the best in the catalog — rather than the smallest. The ability to choose down is retained for weak machines and for experimentation, but it is no longer the expected path. The benchmark in Phase 3 is what settles it per machine.

Decided: best model by default, measured before adoption. See sections 8 and 9.

2. RESOLVED — Should transcripts be saved?

Yes, on by default, stored locally. The sermon is published to the church's own YouTube channel, so the transcript is not a secret and treating local persistence as a risk to be opted into would be a false alarm — it just trains people to click past warnings.

Decided: history on by default, with disk caps, per-session boundaries, a WER estimate per session so the history doubles as a quality record, and one-click erase for shared machines. Cloud-upload ceremony reduced to a single accurate mode indicator.

3. How does the sermon audio physically reach the computer?

This determines whether the loopback work is essential or a nicety, and whether the audio source model in Phase 1 is merely incomplete or wrong. A USB mixer interface or a line-in cable is straightforward. Audio arriving over the network from a digital mixer — Dante, AES67, or a Discovery-based multicast feed — is a normal deployment for a church with a digital console, and the source model in Rev 7 now treats it as a first-class case rather than an edge case. If the answer is a network source, the remaining question is whether the platform enumerates it as a capture device at all, or whether the app needs a bridge.

Default: assume a USB interface or line-in, and support Windows Stereo Mix and Linux monitor sources for the cases where the machine is also playing the service audio.

4. Is the third suggestion lane (sermon note) actually wanted, or is the lyric and verse work enough?

It is the cheapest lane to build and the least certain to be used. Now that history persists, the sermon note has somewhere natural to live at the end of a session, which raises its value slightly.

Default: build it, but keep it visually subordinate so it costs no attention if it is not wanted.

5. Should the assist rail be mirrorable to a stage or confidence display?

The operator might want the transcript on a confidence monitor instead of squinting at the control panel. But anything the operator can see is one more place for a private draft to be seen by the congregation.

Default: control panel only, no output mirroring. Revisit only if asked.

6. Is a second engine (faster-whisper) worth the extra install step?

On capable hardware the argument is weaker than it was — whisper.cpp with a GPU is already fast — but it remains a real win on RAM and on machines where a GPU is unavailable. It also adds a Python prerequisite to an install that is otherwise self-contained.

Default: whisper.cpp only in Phase 2. faster-whisper in Phase 8, opt-in within opt-in, and benchmarked against whisper.cpp through the same contract so the comparison is real.

7. Should the reference clip be the church's own pastor?

The bundled clip is generic. Benchmarking on a real recording from the actual room and the actual voice would be the most accurate possible result, and it is a genuinely compelling feature.

Default: Phase 9. "Benchmark with your own audio" is a strong Phase 9 stretch item, provided the user supplies the file and it never leaves the machine.

RESOLVED — Which local providers does the user get to choose from?

All of them, across two axes. The where selector is this device, a device on this network, or the cloud. The who selector is a catalog of local runtimes — whisper.cpp, sherpa-onnx, an OS on-device provider that needs no install and no download, Vosk for old hardware, faster-whisper where Python exists, and a custom-command escape hatch — with the model list filtered to whichever provider is chosen.

Decided: section 8.1 for the axes, section 8.2 for the catalog, D10 and D11 for the reasoning, Phase 9 for the build. Local leads the settings surface rather than being a fallback beside a cloud form.

Should the OS on-device provider be the default when available?

It is the only provider that needs no install and no download, which makes it the truest answer to “I just want this local”. Against that: quality and availability vary by platform, OS version, and locale, so a default that quietly underperforms would be worse than a default that is merely large.

Default: not the default, but offered first and labelled with what was actually detected — never assumed. If the probe finds it, the user is told plainly that it needs nothing installed and can try it in one click; if the probe does not, the app says so rather than falling back silently.

RESOLVED — Should the engine ever run on another machine?

Yes, as Mode C: a dedicated booth PC with a discrete GPU, capturing the pastor's mic directly and sending only text over the church LAN. It is the cleanest deployment because it removes inference from the operator machine entirely, which dissolves the largest live-safety risk in the plan, and it improves capture quality for free by taking the signal before it crosses a mixer and a resampler.

Decided: added as section 3.1 and Phase 8, after the release pipeline — because a second machine cannot have its engine updated independently until Phase 7 exists. The contract is unchanged; only the transport differs. Mandatory session key, loopback by default, because the church LAN is not a trusted network during a service.

8. Should this graduate out of Experimental immediately?

The existing ExperimentalSection precedent is a good hiding place for iteration, but a feature this visible in the main UI is not really experimental once Phase 4 lands.

Default: own settings section from the start, feature flag off by default, and graduate the flag off after one release cycle of real use.
