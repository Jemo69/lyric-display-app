01 // THE TACTICAL VERDICT: TWO DIVERGENT ENGINEERING PATHS

EXECUTIVE SUMMARY

Let me break it down immediately without marketing fluff. FreeShow and LexDisplay started from related church presentation DNA, but when it comes to handling Scripture, they made diametrically opposed engineering decisions.

FREESHOW (UPSTREAM) PRESENTATION DOMINANT

What it is: A feature-dense, Svelte 3 renderer-bound monolith. FreeShow outsources its Bible core to the external json-bible NPM package and an ancient 2006 browser-based DOMParser converter script.

  • The Good: Incredible presentation ergonomics. Parallel Bible collections, cross-chapter reference expansion (Gen 1:26-2:3), and an HTML tokenizing tag-stack splitter that never breaks Words of Jesus in red.
  • The Ugly: 4-stage XML parsing in the browser renderer thread that allocates 4x memory on 15MB Bibles and chokes the UI frame budget.
LEXDISPLAY (LOCAL FORK) ENGINEERING DOMINANT

What it is: A hardened React/Zustand system built for zero dropped frames during live services. LexDisplay runs a dedicated streaming C/V8-optimized fast-xml-parser engine and offloads full-text search to a Web Worker.

  • The Good: O(1) map indexing (bookMap, chapterMap, verseMap), background Web Worker inverted token search, IndexedDB client caching, and active memory pruning.
  • The Gap: Missing cross-chapter verse ranges, lack of multi-Bible parallel slide layouts, and plain-text verse splitting that strips formatting.

02 // THE XML ENGINE ROOM: FAST STREAMING VS 4-PASS DOM SERIALIZATION

CRITICAL PERFORMANCE

Guess what happens when an unsuspecting church media volunteer imports a 18MB Zefania or OSIS XML Bible during a Sunday service rehearsal? In FreeShow, the entire Electron renderer thread freezes solid for several seconds. In LexDisplay, the UI never even hiccups. Here is the technical reason why.

[!] ARCHITECTURAL FLAW: FREESHOW'S 4-PASS PARSING TRAP

FreeShow's XML parsing engine in src/frontend/converters/xml.ts relies on Stefan Goessner's legacy 2006 script. It does not parse XML into data in one pass. Instead, it executes a four-pass memory marathon inside the browser's JavaScript UI thread:

  1. Pass 1: Runs new DOMParser().parseFromString(xml, "text/xml"), creating hundreds of thousands of native C++ DOM nodes.
  2. Pass 2: Recursively walks the DOM tree (X.toObj) to assemble an intermediate JavaScript object.
  3. Pass 3: Recursively serializes the object into a giant raw JSON string using string concatenation (X.toJson).
  4. Pass 4: Executes native JSON.parse(json) to construct the final object.

If the XML contains unexpected escaped strings (such as ProPresenter metadata with unescaped slashes), Pass 4 throws a syntax error. FreeShow literally has to monkey-patch this with json.replaceAll("N\\A", "") at line 165!

FREESHOW: src/frontend/converters/xml.ts (The 4-Pass DOM Loop) TYPESCRIPT / CLIENT RENDERER 
// Pass 1: Browser DOMParser instantiation
function xmlParser(xml: string, removeBreaks = false) {
    const parser = new DOMParser()
    // ... string slices ...
    return parser.parseFromString(xml, "text/xml").children[0]
}

export function xml2json(xmlString: string, removeBreaks = false) {
    let xmlData: any = xmlParser(xmlString, removeBreaks) // Pass 1
    // Pass 2 & Pass 3: DOM walk and string concatenation into JSON format
    let json = X.toJson(X.toObj(X.removeWhite(xmlData)), xmlData.nodeName, "\t")
    json = "{" + json.replace(/\t|\n/g, "") + "}"
    json = json.replaceAll("N\\A", "") // Band-aid for bad escape crash

    let parsedJson: any = {}
    try {
        parsedJson = JSON.parse(json) // Pass 4: Re-parse synthesized string
    } catch (e: any) {
        console.error("JSON parse failure in XML conversion:", e)
    }
    return parsedJson
}

Now examine LexDisplay's implementation in shared/bible/xmlUtils.js. We completely discarded the browser DOMParser pattern in favor of fast-xml-parser v5:

LEXDISPLAY: shared/bible/xmlUtils.js (Headless Single-Pass Engine) JAVASCRIPT / DUAL-ENVIRONMENT 
// Zero DOM dependencies. Runs headless in Node, Express, Worker, or Browser.
const XMLParser = await loadParser();
if (XMLParser) {
  parser = new XMLParser({
    ignoreAttributes: false,
    attributeNamePrefix: '@_',
    textNodeName: '#text',
    ignoreDeclaration: true,
    parseAttributeValue: true,
    parseTagValue: true,
    trimValues: true
  });
}

export function xml2json(xml) {
  if (!parser) return null;
  // Single-pass direct AST generation. Zero intermediate JSON strings.
  return parser.parse(xml);
}

03 // BIBLE DATA MODEL: ARRAY ITERATION VS O(1) INDEXED MAPS

MEMORY & LATENCY

What I'm trying to say is: a data structure is not just a type definition; it dictates your frame-time during live operations. Let's look at how both codebases structure an entire Bible in memory.

FREESHOW: NESTED ARRAYS src/types/Bible.ts 
export interface Bible {
    id?: string
    name: string
    metadata?: { [key: string]: string }
    copyright?: string
    books: {
        number: number
        customName?: string
        name: string
        abbreviation?: string

            number: number
            verses: {
                number: number

Access Pattern: Linear search. Navigating to John 3:16 requires traversing 43 book array elements, then 3 chapter array elements, then 16 verse array elements: O(B + C + V).

LEXDISPLAY: DUAL MAP ACCELERATION shared/bible/index.js 
// LexDisplay automatically injects O(1) lookup tables
result.bookMap = {};
for (const book of result.books) {
  result.bookMap[book.number] = book;
  book.chapterMap = {};
  for (const chapter of book.chapters) {
    book.chapterMap[chapter.number] = chapter;
    chapter.verseMap = {};
    for (const verse of chapter.verses) {
      chapter.verseMap[verse.number] = verse;
    }
  }
}
result.searchIndex = buildSearchIndex(result);

Access Pattern: Immediate pointer dereference: bookMap[43].chapterMap[3].verseMap[16]: O(1) constant time.

[■] MEMORY HYGIENE: ACTIVE EVICTION VS PERPETUAL CACHE

Here is another massive architectural divergence. In FreeShow, every Bible ever opened stays stored forever in the renderer's Svelte store: export const scripturesCache: Writable<{[key: string]: Bible}> = writable({}). If a church has 8 translations installed (KJV, NIV, ESV, NLT, NASB, CSB, NKJV, MSG), that's roughly 180MB–250MB of active heap memory held continuously by the renderer!

In LexDisplay, we built an active memory pruning and eviction system into src/context/BibleStore.js:

  • IndexedDB Persistence: Full Bible bodies live safely on disk in IndexedDB via src/utils/db.js.
  • Metadata Separation: The store only retains lightweight titles and IDs in bibleMetadata.
  • Eviction Routine: The moment a user switches translations, evictInactiveBibles() purges inactive translations from RAM unless a search modal actively claims ownership via setSearchAllOwner().

05 // VERSE SLICING & PRESENTATION: THE GENIUS OF FREESHOW'S HTML TOKENIZER

PRESENTATION DESIGN

Now let's give credit where credit is earned. This is where FreeShow completely outclasses most open-source worship presentation tools, and where LexDisplay needs to adopt its battle-tested techniques immediately.

[★] FREESHOW'S SECRET WEAPON: splitHtmlText & THE TAG STACK

In many Bible formats (especially OSIS and modern study editions), the Words of Christ are wrapped in styling tags like <span class="wj">...</span>. What happens if verse 16 is 400 characters long and has to be split into two slides?

A naive string split slices right through the middle: Slide 1 has an unclosed <span class="wj"> that bleeds red text over the rest of the display, and Slide 2 has a dangling </span> that breaks DOM layout!

FreeShow solved this flawlessly in src/frontend/components/drawer/bible/scripture.ts using an HTML tag stack tokenizer:

FREESHOW: src/frontend/components/drawer/bible/scripture.ts (Tag-Safe Slide Splitting) TYPESCRIPT / PARSING LOGIC 
function splitHtmlText(value: string, maxLength: number, tolerance: number = 0) {
    const tokens = tokenizeHtml(value)
    const segments: string[] = []
    let current = ""
    let currentLength = 0
    const openTags: { name: string; tag: string }[] = []

    // Helper functions track nesting and synthesize closing/reopening tags
    const reopenTags = () => openTags.map((entry) => entry.tag).join("")
    const closeTags = () => openTags.slice().reverse().map((entry) => `</${entry.name}>`).join("")

    const flushSegment = () => {
        const textContent = current.replace(/<[^>]+>/g, "").trim()
        if (textContent) segments.push(current + closeTags()) // Close opened tags on slide 1
        current = reopenTags() // Automatically reopen tags on slide 2!
        currentLength = 0
    }

    tokens.forEach((token) => {
        if (token.type === "tag") {
            current += token.value
            updateTagStack(token.value, openTags) // Track tag hierarchy
            return
        }
        // ... character slice handling ...
    })

    return segments
}

ADDITIONAL FREESHOW PRESENTATION SUPERPOWERS

  • Dangling Bracket Prevention (getDanglingBracketInfo): In KJV and NASB, bracketed words like [and he said] denote words added by translators. If a slide cut occurs inside a short bracketed phrase (< 4 words), FreeShow shifts the entire bracketed phrase to the next slide rather than severing it.
  • Stage Display Lookahead: FreeShow automatically injects the prior 3 and next 3 verses into the active verse buffer (includeCount = 3), allowing stage confidence monitors to display the upcoming scripture line before the operator advances.
  • Versification Offsets for Collections: When pairing a Protestant translation (66 books) with a Catholic or Orthodox translation on the same slide, verse numbers in Psalms often diverge by 1. FreeShow allows per-chapter offset overrides (offsetId = `${id}-${book}-${chapter}`).
  • Cross-Chapter Reference Resolution: FreeShow's expandCrossChapterSegment() parses spans like Genesis 1:26-2:3 and Romans 8:38-9:2 into discrete per-chapter slide groups automatically.
