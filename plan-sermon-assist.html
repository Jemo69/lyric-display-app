1The Goal

Sermon Assist gives the operator a one-tap Bible verse suggestion when the pastor cites or quotes scripture mid-sermon. That's the whole product. It is a helpful add-on to a focused projection tool — not a transcription suite, not captions, not a sermon archive.

Bible verses onlyOne suggestion type
Manual sendNever auto-displayed
Out of processThe model is not the app
Memory onlyNo transcript on disk

The operator's pain is concrete: the pastor says "First Peter five, verse seven", and someone has about four seconds to find the translation, resolve the reference, and get it on the screen. Sermon Assist does the finding. The operator keeps the judgment — one tap on SEND pushes the verse through the Bible pipeline that already works.

The heavy part — speech recognition weights, the inference runtime, the download, the process lifecycle — runs in an engine that is not in the installer, not in package.json, not in git, and not running until the user asks for it. Everything the user touches — the settings page, the model picker, the suggestion rail — lives in the app.

Success looks like: a suggestion lands in the rail within ~3 seconds of the reference being spoken, it's the right verse, the operator taps send, and the congregation never sees a wrong verse.

2Notes — Vocabulary and Direction

These are the requester's own words. The plan bends to this vocabulary, not the other way around.

Your wordsWhat it means in this plan
"suggest"A one-tap offer shown to the operator. Never auto-displayed, never a wall of text. The word suggest is load-bearing: this is a co-pilot, not captions.
"the pastor said"Live sermon audio entering a microphone on the operator machine — a USB/room mic or the soundboard's aux/mix into line-in. Captured in the renderer with Web Audio.
"local model" / "the size"A downloadable speech model chosen from a catalog with real numbers: download size, RAM cost, relative speed. Five sizes, tiny to large-v3-turbo. Default: small.
"cloud"Switch transcription to a cloud provider instead of running local. Deepgram and OpenAI out of the box, plus a custom endpoint slot for self-hosted or church-local services.
"bible verse selection"The one kind of suggestion. A resolved reference — book, chapter, verse — with its text, ready to send through the existing Bible verse path.
"plugin or another application"The engine. An app-managed optional package the app downloads, verifies, and supervises as its own process. The user never hunts for a separate installer; the app owns the lifecycle.
"model setting"Settings that live in the app: model catalog and downloads, cloud provider and keys, microphone choice, on/off switch. A first-class SERMON ASSIST section in User Preferences.
"not installed by default"Enforced mechanically, not by convention. Zero installer weight, zero new dependencies, zero model files, no mic, no network — until the user opts in. Backed by tests that fail CI.

Project direction: LyricDisplay stays a focused projection tool — fast, volunteer-safe, worshipful restraint. Sermon Assist is a helpful add-on, not a headline feature. That's a scope governor on this plan: one suggestion type, one runtime, no plugin marketplace, no sermon archive. If a decision makes the tool feel like a transcription suite, the decision is wrong.

4Architecture at a Glance

Two halves with one job each. The app decides what matters and what gets displayed. The engine turns audio into text and knows nothing about Bibles. If Sermon Assist were removed tomorrow, the app loses a rail and a settings section — nothing else moves.

Why audio is captured in the renderer

Because the browser already solves the hard parts: device enumeration, permission prompts, resampling. getUserMedia gives a device picker for free, an AudioWorklet emits clean PCM frames, and the mic permission prompt comes from the OS, not from us. The engine stays honest — bytes in, text out — which means it can be swapped, killed, or never installed at all.

Why cloud does not go through the engine

If switching to cloud required the engine to be installed, then "switch to cloud" would not be a switch — it would be a reinstall. Cloud is an HTTPS or WSS call with a key. The key lives in the main process (main/providerCredentials.js, keytar + encrypted fallback), audio flows through main/speech/cloudProviders.js, and the renderer never sees a secret. Local and cloud are two backends behind one transcript hub; switching mid-service is a settings toggle.

Why the engine is a child process and not a library

Native inference blocks, leaks memory, and occasionally dies. None of that is allowed to touch the projection app during a live service. The engine is spawned and supervised exactly like the existing backend: main/backend.js already forks, health-checks, and SIGTERMs a child with an EADDRINUSE story and a 180-second patience window. main/speech/engineProcess.js mirrors that file. When the engine dies, the app shrugs, shows a status chip, and keeps projecting lyrics.

5The Not-Installed-By-Default Guarantee
The constraint most likely to erode

Every one of these is an automated test that fails CI. A README note is not a guarantee — eighteen months of ordinary feature work eats README notes.

  1. Zero new runtime dependencies. A test asserts package.json gains no speech, ML, or audio packages. The engine is not an npm module. The only new bytes in the app are shared/speech/modelCatalog.js (~4 KB of JSON).
  2. No model files or engine binaries in the repo or build output. A test walks the packaged app resources and fails on *.bin, ggml-*, or engine executables.
  3. The master switch defaults to off. Store test: sermonAssistEnabled === false on a fresh profile.
  4. No microphone before opt-in. audioCapture.js has exactly one entry point and it is gated on the flag; a test asserts getUserMedia is never called while disabled.
  5. No network while disabled. Cloud providers and the engine downloader are unreachable while the flag is off; a test asserts no fetch/WS construction in the disabled state.
  6. Nothing about the sermon is persisted. Store test asserts the transcript and suggestion slices are excluded from persistence — no localStorage, no electron-store, no files.

The UI precedent already exists: ExperimentalSection in UserPreferencesModal.jsx is off by default, hidden until opted in, with a toast on enable. Sermon Assist follows that exact rhythm — but as its own first-class section, because it is a real feature with real settings, not an experiment.

What "off" means in practice: the app you ship is byte-for-byte the app we have today, plus one settings entry that says "not installed". No mic indicator, no background process, no model directory, no traffic.

6Where It Lives in the UI

6.1 The assist rail

A slim collapsible strip in the control panel, mounted like the existing ConnectedOutputsStrip. It shows three things and nothing else:

  • Status chip — OFF ENGINE READY LISTENING — LOCAL LISTENING — CLOUD. When cloud is active, the chip names the provider. Honest, glanceable, one word more than the bare minimum.
  • Transcript tail — the last few seconds of what it heard, in muted text. Provisional text is visually provisional (dashed underline) until it finalizes. This is how the operator knows the feature is actually hearing the room.
  • Verse cards — one card per suggestion: reference in bold, verse text truncated to fit, confidence-free plain language ("Sounds like First Peter 5:7"), and two buttons: SEND (solid black) and IGNORE (outlined).

Send is one tap and goes through the existing verse path (handleBibleVerseSelect → emitBibleVerseLoaded) — the same route a hand-picked verse takes, including parallel translations and slide splitting. Ignore dismisses the card and feeds the dedupe: the same reference won't re-suggest for a cooldown window. Keyboard: arrow keys move between cards, Enter sends the focused card, Escape ignores it.

The rail never renders on output windows. Suggestions are operator-side, full stop.

6.2 The settings surface

A SERMON ASSIST row in the User Preferences sidebar (SIDEBAR_SECTIONS), rendered as its own section. Contents, in order:

  • Master switch — off by default. Enabling shows the standard toast and reveals the rest.
  • Engine status + install — "Not installed → Install speech engine", then "Engine v1.2.0 · 12 MB · Remove". Lifecycle lives here: install, update, remove.
  • Model catalog — the five-model table with real download sizes, RAM cost, relative speed, and a DOWNLOAD / active / DELETE state per row. This is the "choose the size" surface, first class.
  • Microphone — device picker (OS names) with a live input meter so the operator can verify the soundboard aux is actually hot before service.
  • Transcription mode — Local / Cloud switch. Cloud reveals provider (Deepgram / OpenAI / Custom endpoint) and the key entry field. Custom reveals URL + key + format.
  • Privacy line — plain sentence: "Audio stays on this computer." or "Audio is sent to Deepgram." The only privacy feature that actually works is one that's true and visible.

Model settings and suggestions live in the app. The engine is infrastructure — the operator sees a status chip, never the word "engine" in a workflow.

6.3 The not-installed state

Before anything is installed, the rail says one line: "Sermon Assist is off. Enable it in User Preferences." No upsell, no nags, no toast. A focused projection tool doesn't beg.

7Model Catalog

Static JSON in shared/speech/modelCatalog.js. Weights are never in the app — the catalog only knows names, numbers, and upstream URLs. Download figures are the published upstream GGML sizes; RAM and speed columns get re-measured on real machines during Phase 2 and corrected in the catalog before ship. Don't ship a number you haven't seen.

ModelDownloadRAM (approx.)Relative speedNotes
tiny~75 MB~0.3 GBFastestWeak on book names. Fine for a smoke test on old hardware.
base~142 MB~0.4 GBFastUsable references, occasional book-name slips.
small~484 MB~0.8 GBBalancedDefault. Reliable on "First Peter 5:7" style references on CPU.
medium~1.5 GB~2.1 GBSlow-ishFor big machines and hard audio — distant mics, heavy room echo.
large-v3-turbo~1.6–3 GB~2.5 GBSlowestBest accuracy on odd book names and accents. CPU is fine but sips patience.

Default is small, not tiny. Verse detection lives or dies on book names — "Habakkuk" is not "a bag of cucumbers" — and small is the cheapest model that handles them consistently. Size anxiety is handled by showing real numbers in the picker; a volunteer can see at a glance what they're downloading and what it costs in RAM. Model switches take effect on the next utterance; no restart.

Downloads are resumable, checksum-verified, and cached in userData/speech-models/. Delete any model from the settings row; the active model cannot be deleted while listening.

8Cloud Mode

Cloud is a backend for the same transcript hub, not a different feature. The switch is a settings toggle; the rail behaves identically. Keys are bring-your-own and stored through the existing credential stack (main/providerCredentials.js — keytar with an encrypted-file fallback). No keys in the renderer, no keys in the catalog, no telemetry of any kind.

ProviderTransportFitKey
DeepgramStreaming (WSS)Lowest latency — partials land like a live caption feed, which is what suggestion detection wants.BYO, keytar
OpenAIChunked HTTPSDead simple, accurate, no streaming to reason about. ~2–4 s suggestion latency.BYO, keytar
Custom endpointWSS or chunked HTTPSWhatever the church already runs — a self-hosted whisper server, LocalAI, a LAN box in the rack. URL + key + format.Optional

The custom slot is the escape hatch and it matters more than it looks: "in case there want something local" is exactly right. A church with no outbound internet can point the app at a transcription service on their own network and get the full feature without the engine. The privacy line in settings says which one is true right now: "Audio stays on this computer", "Audio is sent to Deepgram", or "Audio is sent to 192.168.1.40".

Mid-service switching is allowed and safe: the router cuts over between utterances, never mid-word.

9Files Created

Shared — the only new bytes shipped in the app

  • shared/speech/engineContract.js Engine protocol v1: endpoint names, partial / final / vad / error message shapes, version-negotiation constants, frame format (16 kHz mono PCM s16le). Shared by main and tests so the contract can't drift.
  • shared/speech/modelCatalog.js The five-model table: id, label, download bytes, RAM bytes, quantization, upstream URL template, checksum source. Static, ~4 KB, no weights.

Main process — the speech module

  • main/speech/index.js Module wiring: registers IPC, owns lifecycle, exposes start() / stop() to main.js. Follows main/ndi/ directory style.
  • main/speech/engineInstaller.js Engine package download from the GitHub releases manifest, SHA-256 verification, extraction to userData/speech-engine/, version checks, remove. No execution of anything unverified.
  • main/speech/engineProcess.js Child-process supervisor mirroring main/backend.js: spawn, readiness handshake, health polling, SIGTERM→SIGKILL escalation, crash reporting to the renderer.
  • main/speech/modelManager.js Model weight downloads: resumable, checksum-verified, cached in userData/speech-models/, list/delete/active-model bookkeeping.
  • main/speech/audioRouter.js Takes PCM frames from the renderer and routes them to the engine (local) or a cloud provider (cloud). Cutover happens between utterances.
  • main/speech/transcriptHub.js Normalizes partial/final events from either backend into one event shape, maintains the in-memory rolling window (~2 min), fans out to windows via webContents.send. Holds nothing at rest.
  • main/speech/cloudProviders.js Deepgram (WSS streaming), OpenAI (chunked HTTPS), custom endpoint (WSS or HTTPS). Plain fetch and WebSocket — no provider SDKs. Keys via main/providerCredentials.js.
  • speech-engine/ Build scaffold for the engine package: wrapper config, per-platform build scripts, and the pinned upstream whisper.cpp revision. Not part of the app bundle, not an npm dependency, never in the installer.
  • .github/workflows/speech-engine-release.yml Builds per-platform engine packages on speech-engine-v* tags, publishes a signed-off releases.json manifest with SHA-256 sums.

Renderer — capture, state, and the UI

  • src/speech/audioCapture.js The single mic entry point. Device enumeration, getUserMedia, AudioContext at 16 kHz mono, resampling, frame slicing. Gated on the master flag; starts and stops cleanly.
  • src/speech/worklets/pcm-worklet.js AudioWorklet processor emitting Float32 frames → s16le PCM. Off the main thread, no GC churn.
  • src/speech/verseSuggester.js Pure module: transcript tail → candidate references. Reuses shared/bible (REFERENCE_REGEX, cross-chapter ranges, fuzzy book-name matching) against the active translation; scores, ranks, dedupes. No React, no I/O — trivially testable.
  • src/context/SpeechStore.js Zustand store. Settings slice (persisted: flag, model id, mic device, cloud mode, provider, endpoint) and live slice (never persisted: transcript window, suggestions, engine status).

Renderer — components

  • src/components/Speech/SermonAssistSettingsSection.jsx The User Preferences section: master switch, engine status, catalog, mic picker, mode switch, privacy line.
  • src/components/Speech/ModelCatalogList.jsx The five-row model table with download / active / delete states and real numbers.
  • src/components/Speech/CloudProviderSettings.jsx Provider picker, key entry, custom endpoint fields. Secrets never render back as plain text.
  • src/components/Speech/EngineStatusChip.jsx One-glance state: off, installing, ready, listening (with backend name), engine down.
  • src/components/Speech/TranscriptTail.jsx The muted "what it heard" line, provisional vs final styling.
  • src/components/Speech/SermonAssistRail.jsx The collapsible control-panel strip: chip, transcript tail, verse card queue, keyboard nav.
  • src/components/Speech/VerseSuggestionCard.jsx One card: reference, verse preview, SEND, IGNORE.

Tests

Phase 4 Local Transcription Shippable

Wire the engine to real audio and get text on screen — provisional where it's provisional.

Phase 5 The Rail — Verse Suggestions End to End Shippable

12Testing

Vitest, colocated under src/**/__tests__/ and tests/, matching the existing layout. Three tiers:

  • Pure logic — verseSuggester.js, engineContract.js, catalog validation. This is where the accuracy work happens: a spoken-reference corpus ("First Peter five verse seven", "1 Pet 5:7", "First Peter chapter five", "Genesis one to three") and a negative corpus that must never suggest ("John came over yesterday", "turn to page twelve", "three, two, one").
  • Component and store — rail states, keyboard nav, flag gating, persistence split, settings round-trip.
  • Invariants — the six guarantees. These are the plan's immune system.

Manual is a first-class tier here, because the hard failures are physical: a real mic, a real room, a real pastor's cadence. The Phase 7 dry run is not optional. Accuracy claims get made from a recorded reference clip run through the pipeline — book/verse detection rate, time-to-suggestion — not from vibes.

Regression guard: src/components/Bible/__tests__/BibleImportButton.test.jsx and tests/UserPreferencesModal.test.jsx must pass untouched. Per AGENTS.md, the Bible import surface is permanent product surface — Sermon Assist lives beside it, never over it.

13Risks and Live Safety
RiskMitigation
False verse suggestionsBook-name confidence thresholds, dedupe cooldown, max 3-card queue, one-tap ignore. The operator is the classifier of last resort — and the design assumes the suggestion is often wrong and always cheap to refuse.
The wrong person is heardThe mic points at the soundboard aux, not the room. Documented in setup: "feed it the pastor's channel, not the congregation mic."
Engine dies mid-serviceStatus chip flips to ENGINE DOWN; app keeps projecting. This is the normal failure mode, not an emergency. Live test in Phase 7.
Model too slow on weak hardwareReal numbers in the catalog, one-step model swap, default small. Tiny exists for exactly this machine.
macOS Gatekeeper / Windows SmartScreen on the engine binarySigned builds in the release workflow, checksum verification at install, honest error copy when blocked. Known before Phase 2 ships, not discovered in a church office.
Whisper hallucination on silenceVAD gating in the engine contract; empty/noise segments never reach the suggester.
Privacy surpriseMemory-only transcripts, keytar-held keys, and the always-visible privacy line. Cloud never activates without an explicit settings action.
Scope creep toward a transcription suiteThe plan's own vocabulary — "focused projection tool", "Bible verses only" — is the review checklist. Lyric matching and sermon notes are deliberately not phases; they're a different plan if ever.
14Open Questions
  • 1 · GPU builds? Phase 2 ships CPU-only engine packages. CUDA/Metal builds double the release matrix and the support surface. Recommendation: CPU-only until someone's machine actually can't keep up. Not blocking.
  • 2 · Accept hotkey binding The rail has Enter/Escape when focused. Should there be a global hotkey to accept the top suggestion without focusing the rail (like the existing hotkey system)? Nice for solo operators. Not blocking.
  • 3 · How far does the rail travel? v1 is desktop-control-panel only. Mirroring suggestions to a stage display or mobile controller is out of scope and would need the same trust model as drafts. Not blocking.
  • 4 · Reference clip for accuracy numbers Phase 7 measures detection rate against a recorded clip. Whose voice? Recommendation: a synthetic read of 40 reference forms plus one real recording the requester supplies — measured numbers, not marketed ones.
