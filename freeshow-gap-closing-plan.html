LyricDisplay 6.10.0 · Implementation Plan · October 2026

Closing the FreeShow Gap

A head-to-head comparison of FreeShow's Smart feature against LyricDisplay's Sermon Assist found three real gaps: detection quality, engine capability, and intelligence. This plan closes all three — without adopting FreeShow's worst idea.

The verdict from the comparison stands and is not up for revision: LyricDisplay's staging-only, never-auto-present stance is better and stays. Everything here is additive. No output code changes, no new runtime dependency in the app bundle, and the four hallucination gates remain authoritative over anything this plan adds.

The Verdict

FreeShow has the better-engineered detection system and the worse product for a sanctuary. Its detector is a genuine inverted-index matcher with IDF weighting, n-gram phrase bonus, and competing-candidate disambiguation. Its safety model is a well-worded LLM prompt, and it ships a dropdown that puts unreviewed machine text on the projection screens.

So the port is selective by design: take the matching engine, take the real ASR runtime, take the quote-lane idea — and leave the auto-present path, the unconditional mishearing substitutions, and the 1–100 trust score exactly where they are. Every number the new detector emits is a match quality, never a trust level. It becomes one factor in the existing match × segment product and nothing more.

Read the table twice. LyricDisplay wins on four of nine rows. Those four are the reason the product is safe to ship, and the plan is built to add capability without spending any of them.

1.1 The one-paragraph version

FreeShow's matcher is a real search engine and LyricDisplay's is a word-overlap counter. That gap is worth closing and it is cheap — it is a few hundred lines of pure scoring logic running in a worker that already exists. The engine gap is worth closing and it is not cheap. The quote lane is worth closing only if consent is designed first, because it is the first thing in this feature that would send a pastor's words to a third party.

The mishearing trap, stated precisely

FreeShow's COMMON_MISHEARINGS table maps ask → exodus, for → four, mat → matthew, palm → psalm and cha → chapter as unconditional whole-transcript word substitutions. In a live sermon, "we ask, and it is given" becomes "we exodus, and it is given."

LyricDisplay's 28-row table has no such problem because a row only fires when it can pair a heard form with book + chapter + verse. Porting FreeShow's table verbatim buys recall and spends correctness. D5 resolves this.

2. Decision Log

Five decisions, each with what it costs. Every one of these was walked with the user before the plan was written. If you disagree with any, say so now — D2 and D5 are expensive to reverse after Phase A.

D1

Close all three categories

Chosen: detection quality, a real engine, and an LLM quote lane — all three, in this order.

Why: the three are independent risk surfaces, and ordering them cheapest-first means the two that ship on their own also de-risk the one that needs a live service to evaluate. Detection quality is testable offline. The engine is testable on a bench. The quote lane is only testable in front of a real congregation, so it goes last, when the other two are solid.

Given up: nothing, if the phases are respected. Phase B and C are each independently shippable, so a stalled Phase C does not block a working sermon assist.

D2

Two real ASR providers, benchmark decides

Chosen: bind both whisper.cpp GGML and sherpa-onnx/Nemotron behind the existing v1 contract. The user measures both on their own machine; the app recommends the faster one within a stated margin of the best measured WER.

Why: these two are not comparable on paper, and the existing Phase 8 benchmark harness already exists to settle it. sherpa-onnx ships prebuilt native addons and int8 ONNX weights — adoption is a download, and FreeShow's own 19-excerpt benchmarking found it beat the English-only alternative at equal CPU cost. whisper.cpp has the wider model menu and GPU backends. Neither wins everywhere, and the machine in the booth decides.

Given up: a bigger download menu and a two-row benchmark matrix. The models.catalog.json already declares sherpaonnx with zero models, so the schema half of this work is done — Phase B is filling in rows, not inventing a format.

D3

The quote lane is off by default, opt-in per session, always visible

Chosen: a fourth lane that stays off until the operator enables it. Enabling requires explicit consent naming the provider and stating what leaves the machine. While it runs, an indicator names the active provider at all times. Nothing it produces reaches an output without a press.

Why: this is the first feature in the assist rail that would send sermon text to a third party. The existing cloud path sends audio to a transcription provider, which is a different thing with different consent. Defaulting it on would bend D5 and D9 to accommodate a feature, and that is exactly how those decisions die.

Given up: the quote lane will be discovered slowly. Accepted. A congregation feature nobody turns on is better than one that leaks a pastor's private aside to a model provider by default.

D4

The detector emits match quality; the gates stay authoritative

Chosen: the ported detector returns a raw 0–1 match quality. It is the match half of the existing combine(match, segmentWeight) product. THRESHOLDS.suggestion stays at 0.6. The four gates are untouched.

Why: FreeShow's confidence is a 1–100 number that mixes three unrelated things — how well the words matched, how ambiguous the winner was, and a hard baseConfidence = max(score, 85) floor for clean winners. It then sets auto-play thresholds at 75 and 50 against it. "Medium confidence" ends up meaning something different than it reads. LyricDisplay's number is a clean two-factor product, and that property is worth more than fidelity to the reference implementation.

Given up: byte-for-byte parity with FreeShow's tuning. We will not reproduce the 85% floor or the 75/50 thresholds, and Phase A1 has a test asserting they never appear.

D5

Mishearing rows are context-gated, and curated

Chosen: adopt roughly 30 of FreeShow's rows — the ones that only collide inside a Bible reference. Drop every row whose heard form is ordinary English (ask, for, mat, palm, cha). Every substitution must pair with a book + chapter + verse before it fires.

Why: genius → genesis and philamon → philemon are pure wins — nothing else in a sermon sounds like those. ask → exodus corrupts a sentence a pastor might say every week. The gate is not a compromise; it is the same reason the existing 28-row table is safe, and adopting it keeps one mechanism rather than two.

Given up: some recall on transcripts where a book name appears with no numbers. That case was never going to produce a suggestion anyway, because detectVerse requires a complete reference before any detector returns.

Almost nothing. That is the point — the existing seams were built for exactly this kind of addition.

Why the fuzzy lane is the right seam for the IDF index

Detector 3 already runs in src/workers/verseSearch.worker.js with the bible corpus cached across messages. FreeShow's index is built in the renderer and yields to the event loop between books. Porting it into the worker is strictly easier — the worker has no frame budget to protect, so the yield-scheduling code goes away entirely. Same pure-function discipline, same off-thread guarantee, less code.

Invariants this plan must not break
  • Nothing reaches an output without a press. The quote lane gets three buttons like every other card. No lane gets a send-on-detect path.
  • The four gates run before detection, not after. A gated segment produces no suggestion of any kind, quote included.
  • Zero new root dependencies. The index is typed arrays and loops. The engine is out of process. The LLM is fetch.
  • Canned output never looks real. Once a real engine lands, fakeEngine becomes a test fixture behind an explicit flag — and engineTruth.js keeps its teeth.
  • Transcript text never reaches the log. True today, and the quote lane is the first feature where it would be tempting to log a debug sample.

4. Category A — Detection Quality

4.1 A1 — The IDF inverted index

Replace containment scoring in detector 3 with FreeShow's search approach, ported into the existing worker. Same scoring math, one change: it returns 0–1 match quality, not a 1–100 trust score (D4).

What gets ported, and what gets dropped

vocabPool / vocabToIdMap, token IDsYesCore. Map<string,int> keyed on the lowercased token

wordPostingsOffsets / wordPostings as Uint32ArrayYesCore. Turns candidate generation from "scan 31,000 verses" into "scan this word's postings"
verseTokensOffsets / verseTokensYesRequired for the phrase bonus and coverage functions

computePhraseBonus, 1.6× up / 0.65× downYesHighest value-per-line item in the whole port. Contiguous words are the signal; scattered words are coincidence
verseCoverage with an adaptive targetYesStops three common words from scoring a perfect match against a long verse
Competing-candidate ambiguity penaltyYesReturns the runner-up so the rail can say "this was close". See the honesty fix
Upcoming-verse prior (×1.15 / ×0.75 / ×0.5)YesPreachers read forward. This is the single cheapest accuracy win in the port

4.2 A2 — Reference normalization + scoped mishearings

FreeShow's normalizeReferences() runs ten passes over the transcript. Two of them are things LyricDisplay literally cannot do today: inverted references ("verse 16 of John chapter 3") and glued digits ("John 316" → John 3:16). Both are common in how preachers actually speak.

Passes worth porting, ranked by sermon frequency

Every pass is validated against the reference index before committing, so a bogus chapter is rejected, not guessed. That property is worth keeping verbatim — it is what stops "Jeremiah 29" from becoming Jeremiah 29:1.

The chapter-only prohibition

FreeShow's detector returns Book Chapter:1 at 75% confidence when a book and chapter are spoken with no verse. Its LLM prompt separately forbids this outright. LyricDisplay already does the right thing — detectVerse requires a complete reference — so this port must not reintroduce the verse-1 default. A1 has a test: "Jeremiah 29" spoken alone produces no suggestion.

For the mishearing table, the mechanism is a new shared/bible/mishearings.js exporting a pure normalizeMishearings(text, { contextOnly }). Every row declares whether it is context-free (genius, philamon, romance, revolutions, ordinals like turds → third) or context-gated. Gated rows only apply when the surrounding window already contains a book + digits, which is the only situation where a substitution can help rather than corrupt.

4.3 A3 — Close the honesty gap in the UI

This is small and it is the most important non-algorithmic item in Category A. FreeShow shows a 14px conic-gradient confidence pie and nothing else — the operator is asked to trust a colour. LyricDisplay's verse card already shows the resolved text and the translation, which is better. Two additions:

  • Replace the confidence pie with a worded verdict. "Strong match" / "Likely" / "Close — check the text". Never a raw percentage alone, because a percentage invites the operator to treat it as a probability and it is not one.
  • When the runner-up is within 15%, say so. "Also considered: John 3:17." FreeShow computes this and throws it away. On a sanctuary screen, knowing the detector was undecided is worth more than its false confidence.

4.4 A4 — The number dictionary

FreeShow's numberDictionary.ts is 558 lines covering spoken numbers in English, French, Spanish, German, Portuguese, Italian, Dutch, and Norwegian. LyricDisplay's wordsToDigits() covers English only.

LyricDisplay ships in 60+ UI languages and is used by churches across Europe and Africa. An English-only detector is a real functional gap for those users, not a nicety. Port the dictionary as static data in shared/speech/, extend wordsToDigits() to take a locale, and default to the app's current UI locale rather than English.

5. Category B — The Real Engine

This is the big one. speech-engine/index.js currently exits with code 2 on --engine=whisper and the README says the native binding "is a later, machine-verified follow-up". This phase is that follow-up.

B1 — whisper.cpp GGML

All 29 catalog models are already here. This phase is the executor, not the menu.

  • Static prebuilt binary per platform (win / mac / linux), downloaded to userData/speech-engine/bin/ with a SHA-256 manifest.
  • Weights already handled by main/speechDownloader.js — no new download path needed.
  • GGML ggml-*.bin loads in-process; GPU backends (metal / vulkan / cuda) probed at load and reported in /v1/health.
  • Reports wordTimestamps: true and biasSupport: true in /v1/health — which is what enables the lyric and verse lanes through lanesForCapabilities().
  • Hymn-title and book-name prompt bias is the natural home for the prefer list, and it is where the church's own vocabulary belongs.
B2 — sherpa-onnx + Nemotron

The sherpaonnx provider row already exists in models.catalog.json with zero models. Filling it in is pure data plus a driver.

  • Reproduce FreeShow's pinning discipline: an explicit revision, per-file SHA-256, and a model.json integrity stamp verified before load.
  • Nemotron 3.5 int8 streaming transducer is 682 MB across four files. Multilingual, ~40 languages.
  • Silero VAD ships with it — which makes this the better engine for non-English services, and the honest reason A4 matters.
  • Mac x64 is excluded. sherpa-onnx-node does not work on darwin-x64. The catalog row must say so rather than fail at download.
  • Capabilities are honest: FreeShow reports wordTimestamps: null and biasSupport: false for this path, which means lanesForCapabilities() correctly disables the lyric lane with a stated reason. That is the existing capability gate doing its job — do not paper over it.

What happens to fakeEngine.js

It does not get deleted, and it does not stay reachable by accident. It becomes an explicitly-flagged test fixture: --engine=fake still works, but the app will only start it when speech.allowTestEngine is set, and engineTruth.js keeps labelling its output "TEST ENGINE — canned text, not real transcription" wherever it appears.

The reason is uncomfortable and worth stating: the moment a real engine exists, a stale fake engine that quietly answers a start request is the single worst bug this feature could ship. It would report Listening, produce fluent text, and never have heard a microphone. Keep the fixture; make it impossible to reach by accident.

5.1 The benchmark decides, and it already exists

The existing harness measures WER, RTF, compute backend, GPU utilisation, load time, and peak memory against a real reference clip on the user's own machine. Phase B adds both providers to its matrix and nothing else. The recommendation rule already written into the existing plan applies directly: the fastest model within a stated margin of the best measured WER.

This is also how D2 gets de-risked. If sherpa-onnx fails to install cleanly on some machine, whisper.cpp is already there and the benchmark simply never shows it. No user is ever blocked on a single provider.

6. Category C — The Quote Lane

FreeShow's STT_CONTROLLER_PROMPT classifies transcript chunks into scripture | lyrics | quote | announcement | empty and will happily emit a sermon takeaway. Two things about that are worth keeping and one is worth fixing.

What to take from FreeShow's prompt, and what to leave
Prompt ruleVerdictReasoning

6.1 Consent, routing, and what is visible

  • Off by default. A new lane in lanesForCapabilities() with enabled: false until the operator opts in. The rail shows the reason, matching the existing D11 pattern where nothing is ever silently off.
  • Explicit consent names the provider and the payload. Same rule as CloudTranscriptionPanel: the string shown and the string enforced come from one shared source, because a consent dialog that describes something other than what is checked means nothing.
  • Always-visible provider indicator while the lane runs. This is the "accurate, always-visible mode indicator" requirement, and the lane is off in local mode — so this is the honest reading of it.
  • Plain fetch, no SDK. Same reasoning as D6 in the existing plan. Providers are Ollama, OpenAI, Anthropic, and Google; the request shapes are stable and hand-writing them costs less than a transitive dependency tree.
  • Keys in safeStorage. The ciphertext-only keyring already exists in main/speechCloudKeys.js. FreeShow stores LLM keys as plaintext JSON in its ACCESS store; that is a downgrade, not a model to copy.
  • The lane inherits every gate. It runs after gateSegment(). A segment that failed a gate produces no quote candidate either.

7. What We Deliberately Do NOT Take

The valuable part of a comparison is the list of things you looked at and refused.

No

Auto-present, at any confidence threshold

FreeShow's shouldAutoPlay() is a live path to startScripture() — straight to the projection screens. It ships with a sensible default of ask, plus a 30-second suppression window after manual output changes. But the capability exists, it is one dropdown away, and the confidence number driving it is the dressed-up 1–100 score from D4. LyricDisplay has no such path and this plan adds none. A wrong verse on the wall during a service is a worse outcome than the operator typing it.

No

Unconditional mishearing substitutions

ask → exodus and for → four corrupt ordinary sermon English. D5 gates them behind a book + chapter + verse context. A regression test asserts "we ask, and it is given" survives normalization intact.

No

The 1–100 confidence score

A single number conflating match quality, ambiguity, and a floor. LyricDisplay keeps match × segment in 0–1, gated at 0.6, and adds a worded verdict plus an explicit runner-up disclosure instead of a colour.

No

FreeShow's privacy disclosure

Its default settings text says "Everything remains locally on this device unless explicitly mentioned otherwise" while its LLM path uploads transcript chunks to OpenAI, Anthropic, or Google. The accurate string exists in FreeShow's language file but is not in the default disclosure. LyricDisplay's README documents what a live feed captures that the published recording does not, where it goes, and who can read it on a shared laptop — and says plainly that the feature is not usable today. That candour is the standard.

No

LLM-generated slide design

FreeShow can generate slides, overlays, and templates from a prompt. Out of scope. LyricDisplay's lyric editor is a mature, hand-built surface, and an LLM writing into it during a service is a new class of risk with no counterpart to the detection work above.

9. Phases

Phase 1

The IDF Inverted Index

Build the index and swap detector 3 onto it. Pure functions first, worker integration second.

  • src/components/__tests__/QuoteSuggestionCard.test.jsx — three press-activated actions; no output button exists
  • src/components/__tests__/QuoteLaneOptIn.test.jsx — off by default; consent names the provider and the payload; indicator visible while running
Invariants enforced by test, not by convention

Gates stay authoritative

A gated segment produces no suggestion of any lane, quote included. Asserted against deriveSuggestions().

Match quality ≠ trust

verseScore.js contains no 1–100 scale, no 85 floor, and no 75 or 50 thresholds. A source-level assertion.

Chapter-only stays empty

"Jeremiah 29" alone yields no suggestion. Guards against the verse-1 default.

English survives normalization

"we ask, and it is given, for he is good" is byte-identical after normalizeMishearings.

No output path for quotes

The quote card has no sendVerseLive / loadBibleVerse call anywhere in its module graph.

Canned stays labelled

The app refuses to start a canned backend unless speech.allowTestEngine is set, and every surface still shows the test label.

Zero new root deps

The existing dependency-snapshot test covers this. No addition is permitted.

Installer stays clean

The existing build.files assertion still passes: no engine binary, no weights, no catalog of anything but metadata.

Benchmarking is not a test suite

WER, RTF, and GPU utilisation are measurements, not assertions. They belong in the existing benchmark harness where an operator can read them on their own machine, not in CI where nobody looks. CI asserts structure; the harness asserts performance.

11. Risks

R1

A real engine makes a stale fake engine catastrophic

The risk: a leftover fakeEngine answering a start request would report Listening, emit fluent text, and never have heard a microphone. That is worse than no feature at all.

The mitigation: Phase 5 requires speech.allowTestEngine, engineTruth.js keeps labelling every canned surface, and a test asserts the app cannot reach a canned backend by default. Do not relax this in a later phase because "nobody will run the fake engine in production."

R2

The mishearing table gets "improved" into unsafety

The risk: someone adds a row for a real-world miss, does not set the context flag, and ordinary English starts getting rewritten. Recall is visible and good; corruption is invisible until a service.

The mitigation: every row declares its own gate, the "we ask" regression test runs in CI, and the table lives in shared/ where a reviewer sees the whole surface at once.

R3

The quote lane's consent gets treated as boilerplate

The risk: a consent panel modelled on CloudTranscriptionPanel that reads correctly and enforces something else. Then a user believes sermon text stayed local while it did not.

The mitigation: the shown string and the enforced string come from one shared source — the rule already stated in that component's own header comment. A test asserts they are the same object.

R4

sherpa-onnx fails to install on some machine

The risk: a native addon that does not build or run everywhere, leaving a broken row in the provider menu. It already excludes darwin-x64, so the precedent exists.

The mitigation: two providers means one failing is a missing row, not a broken feature. The benchmark only offers what actually started. This is the concrete payoff of D2.

R5

The 682 MB download scares people off

The risk: the model size is a legitimate barrier for a volunteer-led church, and FreeShow does not let the user decline it gracefully enough.

The mitigation: whisper.cpp's small models are 190–265 MB and go first. The catalog already shows real sizes before anything downloads, and the existing install wizard already explains what is about to happen. Nemotron is the choice for a church that wants multilingual, not the default.

R6

Someone re-adds auto-present

The risk: it is genuinely useful, it is one setting, and FreeShow ships it. A future contributor will read that as validation.

The mitigation: PRODUCT.md records the comparison and the verdict in Phase 8. The three press-activated buttons are tested as a structural property of the component, not a convention in a comment.
