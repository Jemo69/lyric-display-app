LYRICDISPLAY — PLAN — PASTOR VOICE SUGGEST

Pastor Voice Suggest: optional transcription sidecar, Bible-verse rail in the app

Let the pastor's mic drive Bible-verse suggestions on screen — without bloating the installer. The heavy work (Whisper models, inference) lives in an optional downloadable sidecar. The app itself only holds two things: the Speech & AI settings and the Assist rail that suggests verses. Nothing ships by default. Nothing hits an output until the operator presses send. And every seam is built to expand — new models, new cloud providers, new suggestion lanes — without a redesign.

1. Goal + vocabulary

Plan name + main goal

Plan: Pastor Voice Suggest — sidecar transcription with in-app Bible suggestions.

Goal: transcribe the pastor (local Whisper model the user picks by size, or cloud API), match the transcript against the Bible library, and show ranked verse suggestions in the control-panel UI for one-click display. Transcription is 100% opt-in: no models, no engine, no extra weight in the default installer.

Vocabulary — the user's words, locked in
  • Sidecar: the optional transcription engine. Downloaded on demand, forked by Electron main. Not in the installer. This is the "plugin / another application" the user asked for — implemented as a versioned folder, not a second app the user must launch by hand.
  • Rail: the Assist rail in the control panel. Shows live transcript + ranked Bible-verse suggestions. Reserves lanes for future Next-lyric and Note suggestions.
  • Model catalog: the pick-your-size list in settings. Each entry shows download size, RAM cost, quality tier. Nothing pre-installed.
  • Suggest: a ranked verse card with Display button. A suggestion is a proposal, never an auto-output.
  • Provider switch: Local vs Cloud picker in settings. Same PCM in, same rail out, different hop in the middle.

Interview confirmed 2026-09-25: sidecar + rail vocabulary, full Whisper catalog, any-provider cloud (OpenAI first as reference), renderer mic capture, first-class Preferences section, Bible-first rail that stays expandable.

2. Non-negotiables

What this plan refuses to do

  • No transcription weight in the installer. No models, no whisper runtime, no engine binaries in electron-builder files. The installer size does not move.
  • No auto-output. A suggestion never touches a projector, stage screen, or NDI feed until the operator presses Display / Jump. The rail is advisory, full stop.
  • No settings buried in Experimental. Speech & AI is a first-class Preferences section with provider picker, model catalog, device picker, and status. Volunteers must find it without a treasure map.
  • No engine-owned mic code. The renderer captures audio portably. The engine is pure compute: bytes in, text out. Any language can implement a third-party engine later.

3. Architecture

One capture point, two provider paths, one suggestion store, one rail. The sidecar is the only new process, and it only exists when the user installs it.

Why a sidecar folder, not a second app

The user said "any packaging that lets me expand in the future." A separate companion app the user launches by hand is the most fragile option: two installers, two updaters, two dock icons, and volunteers will run mismatched versions. A sidecar folder downloaded on demand from versioned releases gives the expansion without the pain: independent release cadence via its own tag namespace, a versioned /v1/health contract so third-party engines can plug in, and one fan-out point in main so multiple windows share transcripts.

Same repo, separate release. The contract, app client, fake-engine fixture, and conformance suite live together so they cannot drift — but engine releases never block behind app notarisation queues.

Why the renderer captures the mic

Cross-platform input capture is a tar pit: WASAPI on Windows, CoreAudio + TCC on macOS, PulseAudio / PipeWire monitors on Linux — and whisper.cpp ships no mic code at all. The browser already solved this portably, and the control-panel renderer is always open during a service. The engine stays a pure compute process. Smaller contract, easier tests, any-language engines later.

Default policy

Default is large-v3-turbo-q8_0: near-best accuracy at roughly 4x the speed of full large-v3. Nothing is pre-installed — the user downloads on demand with progress. The in-app benchmark (Phase 3) measures WER vs RTF on the user's hardware and recommends the fastest model within a stated margin of the best measured. Measurement beats defaults.

6. Contracts (sidecar + cloud)

6.1 Sidecar HTTP (localhost only)

GET  /v1/health   -> { ok, apiVersion, engineVersion,
                      capabilities, loadedModel, device }
GET  /v1/models   -> { installed: [...], diskFreeBytes }
POST /v1/models/:id/download -> { taskId }  (progress over WS)
DELETE /v1/models/:id        -> { freedBytes }
POST /v1/session             -> { sessionId }
POST /v1/session/:id/close   -> { ok }
POST /v1/transcribe          -> batch file (tests + diagnostics)
POST /v1/benchmark           -> { taskId }

6.2 Renderer → engine WebSocket (audio up, text down)

UPSTREAM  binary: LE Int16 PCM, 16 kHz mono,
          100 ms frames (1600 samples, 3200 bytes). No envelope.
DOWNSTREAM JSON, discriminated on "t":
  { t:"ready",   sessionId, model, sampleRate }
  { t:"partial", sessionId, text, tStartMs, tEndMs, confidence }
  { t:"final",   sessionId, text, tStartMs, tEndMs, words?[] }
  { t:"vad",     sessionId, state:"speech"|"silence" }
  { t:"progress",taskId, receivedBytes, totalBytes, mbps }
  { t:"stats",   rtf, encodeMs, decodeMs, loadMs, memoryMb, backend }
  { t:"error",   code, message, fatal }

A partial is a hypothesis — rendered dimmed, last words visibly unsettled. Only a final populates a suggestion. Treating partials as finals is the fastest way to make operators stop trusting the rail.

6.3 Endpointing + versioning

  • Partial roughly every 600 ms of new audio; final on 500 ms silence or 15 s hard cap.
  • Targets (acceptance, not promises): first partial < 1.2 s local, < 800 ms cloud. If hardware misses it, settings says so plainly and recommends a smaller model. Never silently degrade.
  • Health carries apiVersion. App refuses mismatched major, warns on minor, ignores unknown fields. Engine ships on its own cadence.

6.4 Cloud: any provider, OpenAI first

The user said "any provider" — so the server route is a provider adapter, not an OpenAI hard-code. OpenAI Whisper ships first as the reference (fetch + FormData, key in secretManager, never in the renderer), with Groq / Deepgram added behind the same seam. Same PCM in, same rail out. The sermon is published (church YouTube), so the design spends its honesty budget on one thing that matters: a persistent, accurate LOCAL / CLOUD indicator so a volunteer always knows where audio is going. No modal fatigue, no per-session click-through theater.

8. Phases in execution order

Phase 0

Contract + fake engine (no models, no UI)

  • Freeze /v1/* + WS shapes above as the contract doc; add fake-engine fixture + conformance suite.
  • Done when: a third-party engine can implement the contract from the doc alone and pass conformance.
Phase 1

Sidecar scaffold + supervisor (no transcription yet)

  • Create speech-engine/ (own package.json, health + model list/download/delete, stub inference); create main/speechEngine.js fork/health/restart mirroring main/backend.js.
  • Release plumbing: speech-engine-v* tags, per-platform bundles, releases.json manifest with SHA-256, no shared steps with app release workflows.
  • Installer-exclusion CI check: fail if engine/models leak into electron-builder output.
Phase 2

Capture + store (audio flows, words flow)

  • speechAudioWorklet.js + speechAudioCapture.js (16 kHz mono Int16, 100 ms frames, RMS VU, reconnect backoff); useSpeechStore.js ring buffer + history + status.
  • Local path end-to-end against real whisper.cpp on one platform; cloud path stubbed behind the same store shape.
Phase 3

Settings + catalog + benchmark

  • SpeechSettingsSection.jsx + ModelCatalogList.jsx wired into UserPreferencesModal.jsx:1383/1403; download progress, device picker, status block, LOCAL/CLOUD indicator.
  • /v1/benchmark + results table (WER / RTF / first-partial / backend / peak mem) with measured recommendation. Illustrative numbers become real numbers here.
Phase 4

Rail + Bible matching (the payoff)

  • verseMatcher.js (Fuse.js fuzzy match, pure + tested); SermonAssistPanel.jsx transcript + Bible lane, reserved lyric/note lanes; verse Display via existing bibleVerseLoaded path in BibleControlPanel.jsx / LyricDisplayApp.jsx.
  • Interaction tests: suggestion → Display routes correctly; idle rail never emits to any output.
Phase 5

Cloud providers + hardening

  • Server adapter: OpenAI reference, then Groq/Deepgram behind the same seam; keys in secretManager; latency/queue telemetry in the rail.
  • Thermal/CPU-fallback warnings, disk-space guards, offline behavior (Local needs downloaded model; Cloud needs network — both say so plainly).
  • Docs + volunteer runbook: pick a model, pick a mic, press Listen, press Display. Four steps, one page.

9. Acceptance

  • Fresh install contains zero transcription bytes (CI asserts installer size delta ≈ 0).
  • User picks a model by size in settings, downloads with progress, sees active model + engine status.
  • Local/Cloud switch works mid-session; the LOCAL/CLOUD indicator is always correct.
  • Pastor speech → transcript → ranked Bible verse in the rail; Display routes through the existing Bible output path.
  • First partial < 1.2 s local / < 800 ms cloud on reference hardware; misses produce a plain-language recommendation, not silent degradation.
  • Rail idle (or engine absent) changes nothing on any output. Ever.
  • New provider or new model ships without touching the rail layout or the contract major version.

What ships first vs what waits

Phase 1–4 deliver Local + Bible lane + settings + rail. Cloud reference (OpenAI) lands in Phase 5 alongside hardening. Extra providers, Next-lyric auto-follow, and Note drafting reuse the same seams later — no redesign, just new lanes and adapters.
