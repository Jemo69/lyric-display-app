Method 04

Render & Cache

Attack the two render-side costs: recomputed verse text during React renders, and the whole-chapter verse-button DOM.

1 · Memoize the split + text reads

getVerseText() and getFormattedReference() run on every render, and slides are recomputed in a useMemo keyed by that derived text. When combined with set-state toggles (book expand, resize), the split pipeline re-runs even though nothing changed.

  • Compute { text, reference, slides } once at selection time and cache it keyed by (bibleId, book, chapters, verses, splitSettings).
  • Store the computed slides on the selection in the store so renders read an array, not a re-split.
  • Result-cache the split function itself (WeakMap on string key) so identical inputs are O(1).

2 · Virtualize the chapter verse list

Psalm 119 → 176 <button>s, each containing full verse text clipped with -webkit-line-clamp. Every re-render rebuilds the whole list.

OptionEffect
react-window / fixed-height rowsOnly ~15 visible rows in the DOM
IntersectionObserver chunkingProgressive render, no new dependency
Virtualised grid in BibleBrowser tooSame win in the modal browser

3 · Trim the eager search index

buildSearchIndex runs synchronously on the main thread at import and its whole word→positions map is persisted into IndexedDB alongside the Bible. Build it in a worker; store index separately; hydrate chapters lazily instead of loadAllBibles() pulling every Bible into RAM.

4 · Shrink persisted state

bibleHistory embeds full verse text for up to 50 entries in localStorage. Persist { reference, preview, bibleId } only.

Perf expectations

Renders become cheap even during store churn; chapter browsing no longer builds 176 buttons; import no longer blocks the main thread with index construction.
