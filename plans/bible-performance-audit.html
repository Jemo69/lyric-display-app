01 · Where does the app stand vs the reference

The FreeShow reference describes a two-layer verse pipeline:

  • splitLongVerses — breaks one oversized verse into sub-verses (3_1, 3_2…) by char count, punctuation-aware and HTML-safe.
  • smartSplit — paginates the (post-split) verses into template-geometry-aware slides, falling back to versesPerSlide: 3.

One-line takeaway: the app has the settings names from FreeShow but not the system — no sub-verse identity and no geometry-aware smart split. The char budget the user sets is largely defeated by a hard-coded slide cap (see §04).

04 · Critical finding: the maxSegments=3 bug

splitBibleTextIntoSlides calls splitPlainText(text, maxChars, tolerance, 3) — the 3 is a hard-coded cap. The merge loop then combines segments until only 3 remain, so the user-facing longVersesChars=100 setting has almost no effect on long verses.

measured: Esther 6 (~539 ch) with longVersesChars=100
  expected: ~6 slides of ~100 chars
  actual:   263 / 139 / 135 chars in 3 slides   ← budget destroyed

Consequence: every long verse = exactly ≤3 oversized slides, ignoring the setting. This is the single most correctable defect, and it is exactly what FreeShow's splitLongVerses exists to prevent.

05 · Real hotspots beyond the splitter

  1. Per-keystroke structured clone. The search effect posts the entire bibles object (full Bible content) to a worker on every debounced keystroke, and depends on bibles so any store change re-runs it.
  2. Whole-chapter DOM. The whole chapter renders a <button> per verse with full text and -webkit-line-clamp.
  3. Output autosizer. Deep-linking a Bible slide into output triggers maxLinesCalculator binary-search DOM measurement (cache capped at 500).
  4. Non-memoized render reads. getVerseText() / getFormattedReference() re-run every render; slides are recomputed per render instead of persisted.
  5. Eager search index. Built on the main thread at import and persisted/transferred as part of the Bible object; loadAllBibles pulls every Bible into RAM.

06 · Verdict

The architecture is conceptually near FreeShow's, but the two things that make FreeShow's system valuable are missing here: (a) per-verse sub-verse splitting that honours the char budget, and (b) a geometry-aware smart split that removes the expensive downstream autosize. The highest-leverage fixes are:

  1. Fix the budget-breaking cap so longVersesChars means something.
  2. Adopt a punctuation/sentence-aware splitter (never cut mid-word, never cut mid-sentence when avoidable).
  3. Kill the per-keystroke Bible clone in the search worker.
