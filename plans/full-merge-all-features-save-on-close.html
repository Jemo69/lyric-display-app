01 · The promise — nothing gets dropped

The goal of this plan: after the merge, the app has every feature it has today plus every feature upstream shipped. No telemetry for the sake of it, no feature removed to "simplify." The two hard requirements:

  1. Keep all features currently in the app — Bible layer, RCCG TPHB songs, bible splitter, lite controller, custom outputs, bridges, latency fixes.
  2. Keep save-on-close — everything the app persists today still persists after the merge, and is still there the next time the app opens.
RequirementGuarantee method
Keep all current featuresFull feature inventory (see §03) is written as a checklist before the merge; every item must pass a manual test after.
Keep save-on-closePersistence stack is preserved (see §02) — zustand persist + electron-store + server session file. Verified with a close-and-reopen test.

02 · Save-on-close — how it works today and after

Today the app saves state through four independent layers. All four survive the merge unchanged:

LayerWhat it savesWhereMerge impact
1 · zustand persist (renderer)LyricsStore (lyrics, output settings, stage settings, autoplay, performance settings, vim mode, custom outputs), HotkeysStorelocalStorage — zustand default; the persist config sets only name, no custom storageUntouched — same storage, same names
1b · IndexedDB (renderer)Bible content — full Bible texts via src/utils/db.js (idb → bibleDb). BibleStore partialize excludes bibles from localStorage; only metadata/settings/history are persisted to the storeIndexedDB (BibleDatabase)Locked — Bible content stays in IndexedDB, never moved back to localStorage
2 · electron-store (main)Preferences, dark mode, theme, display assignmentsuserData/*.jsonUntouched
3 · Main-process filesRecent files, user templates, encrypted secrets, provider credentialsuserData/Untouched
4 · Server session stateCurrent lyrics, selected line, output enabled, stage settings, registered outputs, live-safetyuserData/backend/realtime-session-state.json (already present in the local config dir)Upgraded — upstream's atomic save is added on top

Key finding — IndexedDB is the Bible's home, keep it there

The Bible layer is the one store that is IndexedDB-backed on purpose. src/utils/db.js opens BibleDatabase/bibles via idb, and BibleStore writes Bible texts there while its partialize deliberately leaves the bibles payload out of localStorage. This is what keeps the app fast and its Bible data separate from settings. The merge rule is absolute:

  • Do not move Bible content back to localStorage.
  • Do not change the idb-backed bibleDb in src/utils/db.js.
  • If upstream's store changes touch BibleStore, keep the same name: 'bible-store', keep the IndexedDB migration, keep the same partialize boundary (content → IndexedDB, metadata → localStorage).

Key finding — server session file

The local config already contains userData/backend/realtime-session-state.json — the server-side session file. Upstream v6.8.1 hardened this with atomic writes (tmp + rename), debounced saves, schema versioning, and storage-failure notifications. Merging it in makes save-on-close more robust, not less.

Only rule

When the merge touches any of the four layers, take the union of fields, never a replacement. E.g. if upstream rewrites the LyricsStore persist schema, keep local fields (customOutputs, vimMode, autoGroupLines…) and add upstream's new fields alongside. And never re-point a store from IndexedDB back to localStorage.

05 · Merge steps

STEP 1

Freeze the feature checklist

Write the local inventory (§03) into a test doc. Every item gets a manual pass/fail. This is the contract: nothing merges until every box is checked.

STEP 2

Clone fresh, keep both histories

# clone upstream once, add local as a remote, keep both histories
git clone https://github.com/PeterAlaks/lyric-display-app.git merge-work
cd merge-work
git remote add local /home/jemo/projects/church_things/lyric-display-app
git fetch local
# new branch on top of upstream v6.8.1
git checkout -b full-merge upstream/master

Do not git merge local/main blindly — no merge-base means a giant conflict pile. Use git checkout local/main -- <paths> to copy the local-only feature files onto the upstream base, then reconcile the four conflict zones by hand.

STEP 4

Reconcile the four conflict zones

  • Modal system: keep upstream ModalProvider; wire local bridges as additional modal sources.
  • Output routing: keep local base: './' + dynamic routes; port upstream output components as routes under it.
  • Server: add upstream server/realtime/*, server/security/*, server/middleware/* as new files; leave local API routes intact; merge secretManagers (local already has one — port upstream rotation/validation into it).
  • Persist schema: take the union of zustand persist fields and electron-store keys.
STEP 5

Merge dependencies (union, not replace)

Add upstream deps: dompurify, unzipper, jszip, @electron/asar, mammoth, paradox-reader, @julusian/midi, use-sync-external-store, @radix-ui/react-slider, @tailwindcss/postcss.

Keep local deps: fast-xml-parser, @tanstack/hotkeys, idb, vitest + testing-library, archiver, smart-buffer, @babel/core, rollup, jsdom.

Keep the local Bun dev shim (destroySoon) and server/package.json entries.

STEP 6

Save-on-close is re-wired, not replaced

  • Keep all four persistence layers (§02).
  • Port upstream server/realtime/sessionPersistence.js (atomic tmp+rename, debounce, schema version).
  • Keep the local close-confirmation flow in main.js and performCleanup() exactly as-is.
  • Verify the local shows.json/setlist/lyrics save paths still write on quit.

Memory rule in this merge

Apply these fixes after the feature port (§05) but before release, one fix per commit, each verified with a memory snapshot. Upstream's memory-growth fixes (log caps, idle-output cost cuts, render-clock fix) complement this list — take both.

Hard rule — do not regress the Bible

The Bible is the worship-critical feature. The memory fixes must never slow it down. From the code, the fast search path depends on bible.searchIndex (shared/bible/index.js:388-421) — without it, search falls into the slow brute-force verse scan (index.js:427-438). Therefore:

  • Active bible stays fully resident — its full text + searchIndex + book/chapter/verse maps must remain in memory. Never evict the active bible.
  • Indexes are never dropped — lazy-build is allowed, removal is not. Dropping the index is a performance regression.
  • Non-active bibles live in IndexedDB and load on-demand, their indexes built once and cached on first use. First "search all" in a fresh session may pay a one-time build per bible; repeat searches must be as fast as today.
  • Search must get faster, not slower — stop sending the entire bibles object to the worker per keystroke (BibleSearchModal.jsx:174-181); send only the active bible + query. This is the biggest current search cost.
  • Load path unchanged — reading a chapter/verse and displaying it on the stage must not add a disk/IndexedDB round-trip on the hot path.

Verification: measure Bible open → search → select → stage-display timing before and after each memory fix. Any fix that makes the active-bible search path slower is rejected.

Expected effect

Lower CPU: text auto-fit off the main thread + cheaper animations + no per-keystroke layout. Lower GPU: no blur re-composites, lighter shadows, fewer re-paints, no full-screen effects per line change. Combined with §07 memory fixes this targets exactly the "stutter on older hardware" complaint in PERFORMANCE_PROPOSAL.md.

New feature — GPU Effects toggle (on/off, no restart)

Add a runtime on/off switch gpuEffects to performanceSettings (default ON) that gates the GPU-heavy effects in §08 — without disabling the app's GPU acceleration and without a restart. Lives in both the User Preferences modal and the Output Settings panel, next to the existing Low Power / Reduced Graphics toggles.

  • OFF = no blur transitions (fall back to fade), no spring animations (use tween), no heavy box-shadows, no backdrop-blur on full-screen modals, video backgrounds stream from disk. Same as "Reduced Graphics + Low Power" for effects only.
  • ON = everything renders exactly as today (full visual fidelity).
  • Applied live in the output windows — toggling it mid-service takes effect on the next line change, no app restart.
  • Independent from disableHardwareAcceleration (app-level GPU off, restart required) — that one stays for broken-GPU escape hatches only.

Implementation touchpoints: src/context/LyricsStore.js:219-224 (add key + default), src/hooks/useStoreSelectors.js:268-276 (auto via existing selector), src/pages/RegularOutput.jsx:293 (gate shouldAnimate + blur variant), src/pages/StageOutput.jsx:300 (gate springs), src/components/UserPreferencesModal.jsx:410-431 and src/components/OutputSettingsPanel.jsx:340-388 (add toggle row).

Hard rule — the look matters

gpuEffects OFF must never make the app look cheap, broken, or different in brand. This is a worship tool projected for a congregation — visual quality is a feature, not a sacrifice. Therefore:

  • Same design language in both modes — identical colors, typography, spacing, layout, and branding. The toggle only changes how things render (GPU cost), never what is shown.
  • Blur → fade must look deliberate — the fallback is a polished cross-fade, not a hard cut. If a blur transition can't be replaced without losing its character, keep the blur and accept the cost.
  • Spring → tween must keep the feel — springs are replaced by tweens tuned to the same duration/easing feel (0.15–0.3s ease-out), so motion still feels smooth and intentional.
  • Shadows never disappear silently — reduced shadows use a lighter, still-elegant treatment (thin 1px border or smaller alpha). No flat, washed-out text on busy backgrounds.
  • Side-by-side proof — every GPU fix ships with a before/after screenshot of the same lyric on a video background. If the OFF frame looks worse, the fix is rejected regardless of CPU/GPU savings.
  • Default stays ON — the congregation-facing default is full fidelity. gpuEffects OFF is an opt-in choice by the operator for specific weak hardware.

Verification

Open Task Manager / top + GPU meter, run a live service with line changes and a video background, and confirm CPU% and GPU% both drop versus the current build. Keep a before/after screenshot of the output to prove visual parity.

Bottom line: this is a union merge — every local feature stays, every upstream feature is added, and the save-on-close stack (zustand + electron-store + server session file) is preserved and hardened with upstream's atomic writes.
