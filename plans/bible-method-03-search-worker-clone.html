Method 03

Kill the Per-Keystroke Bible Clone

The single biggest silent cost in the current Bible layer is not the splitter — it's the search worker being fed whole multi-MB Bible objects on every keystroke.

The problem

In BibleControlPanel.jsx the search effect posts { currentBible, query, bibles, … } to a worker after a 300 ms debounce. The bibles object holds full Bible content (books→chapters→verses). Structured-cloning multiple multi-MB Bibles per keystroke is pure serialization overhead on the main thread — the worker forces it even when it only needs the small search index.

The effect also depends on bibles, so any store write re-arms it.

Fix options (cheapest first)

OptionWhat to sendCost
index-only (recommended)Send each Bible's prebuilt searchIndex + book name/number list, not verse text. The intersect path in searchBible already works off the index alone.Tiny, fast clone
Cache in workerPost each Bible once with a load message; subsequent messages send only { query }.Small, kept-sync bookkeeping
Transferable / SharedArrayBufferMove the index into a transferable buffer.Complex, only if index is huge

Supporting fixes

  1. Fix the effect deps. Re-arm on query / activeBibleId only, not on the whole bibles object.
  2. Cache results keyed by (query, bibleId) — identical keystrokes are free.
  3. Share one worker across BibleControlPanel, BibleBrowser, BibleSearchModal instead of three.

Perf expectations

Sends ~0.1–2 MB of search index instead of ~2–40 MB of verse text per keystroke. Removes jank from rapid typing and from store updates during import/switch.

Note

The reference search path falls back to a triple-nested loop when the query is a combined book + text or when the index is missing — keep the index available to stay on the fast path, or route those queries through the index intersect as well.
